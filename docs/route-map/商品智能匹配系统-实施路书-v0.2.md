# 商品智能匹配系统 - 实施路书

- 版本：v0.2
- 日期：2026-03-27
- 状态：待执行
- 对应需求：`docs/requirements/商品智能匹配系统-需求文档-v0.2.md`

## Objective

- Target outcome：
  交付一个模型主导的商品匹配 MVP，运行在 Windows 本地环境中，能够通过“百炼标准化 + 百炼 Embedding 召回 + DeepSeek 裁决/复核”完成客户商品库与我司商品库的对照，并以“少错配”为第一目标输出结果。
- Source requirements：
  `docs/requirements/商品智能匹配系统-需求文档-v0.2.md`
- Preconditions：
  - 新版需求边界已确认
  - 百炼普通 API Key 与 DeepSeek API Key 可用
  - 当前 MVP 的上传、字段映射、导出骨架已存在
  - 有一批真实样本可用于评测与验收

## Milestones

- Milestone 1：
  冻结模型化数据契约、提供方分工与验收样本。
- Milestone 2：
  跑通标准化与召回链路，生成稳定候选集。
- Milestone 3：
  跑通模型裁决、分级输出和审核导出。
- Milestone 4：
  用真实数据完成效果验收，并决定默认上线策略。

## Phase Plan

### Phase 0 - 需求冻结与评测样本准备

- Goal：
  把“少错配优先”的业务目标、分级口径和评测样本固定下来。
- Why this phase exists：
  如果没有统一的评测口径，后面很容易陷入“感觉模型更聪明”而不是“结果可验收”。
- Inputs required：
  - 已确认的 v0.2 需求文档
  - 真实业务 Excel
  - 过往匹配结果样本
- Tasks：
  - 冻结四级结果状态定义
  - 定义人工标注评测样本集，建议 200 到 500 条
  - 明确 `auto_matched` 精度目标与 Top3 候选召回目标
  - 确认第一版使用百炼普通 key 与 DeepSeek key，排除 Coding Plan key
- Deliverables：
  - 评测样本清单
  - 评测指标说明
  - 结果分级口径说明
- Validation gate：
  项目组可以用同一份样本和同一套口径判断“这次改动到底有没有进步”。
- Risks：
  - 没有统一标注口径会导致后续验收失真
  - 样本集偏科会让模型选择失真
- Rollback or fallback：
  若短期无法凑齐完整样本，先做一版最小评测集，但不得跳过评测定义直接编码。

### Phase 1 - AI 提供方与配置层落地

- Goal：
  建立可配置、可切换、可追踪的模型调用基础层。
- Why this phase exists：
  模型主导架构的前提是调用链稳定，否则后面的标准化、召回、裁决都会失控。
- Inputs required：
  - 百炼与 DeepSeek 的 API 接入信息
  - 当前本地运行骨架
- Tasks：
  - 设计 Provider 配置结构
  - 设计模型分工配置：标准化模型、Embedding 模型、主裁决模型、复核模型
  - 设计超时、重试、限流、错误日志策略
  - 设计本地 API Key 配置存储方案
  - 明确配置页字段与默认值
- Deliverables：
  - Provider 配置契约
  - 模型角色配置契约
  - 错误与日志策略说明
- Validation gate：
  不写业务逻辑的前提下，能够清楚说明“系统如何知道该用哪个模型做哪件事”。
- Risks：
  - 不同模型的 JSON 稳定性差异
  - 直连 API Key 带来的密钥管理风险
- Rollback or fallback：
  若多模型配置复杂度过高，先保留固定默认分工，再在第二阶段开放更多可配项。

### Phase 2 - 标准化链路重构

- Goal：
  用模型主导方式替换原有规则主导标准化逻辑。
- Why this phase exists：
  如果标准化层仍停留在规则抽取，后续召回和裁决的上限仍然会被旧逻辑限制。
- Inputs required：
  - 字段映射结果
  - 标准化 JSON schema
  - 评测样本
- Tasks：
  - 定义标准化输出结构
  - 设计标准化 prompt 与结构化输出 schema
  - 明确原始字段与标准化字段如何并存
  - 定义标准化缓存策略
  - 设计标准化失败时的错误呈现方式
- Deliverables：
  - 标准化字段契约
  - 标准化 prompt 草案
  - 标准化缓存方案
- Validation gate：
  抽查样本时，品牌、商品主词、规格、单位、分类的抽取结果可读、可解释、可复核。
- Risks：
  - 模型会把口语、品牌、商品名互相识别错位
  - 规格和包装层级抽取不稳定
- Rollback or fallback：
  如果一次性输出全部字段不稳定，可拆成两步：先抽主商品信息，再抽规格包装信息。

### Phase 3 - 向量召回链路落地

- Goal：
  构建“先召回再裁决”的稳定候选链路。
- Why this phase exists：
  不先召回候选，裁决模型面对整库会既慢又贵，还容易失控。
- Inputs required：
  - 标准化后的我司商品库
  - 标准化后的客户商品库
  - Embedding 模型配置
- Tasks：
  - 设计召回文本拼装策略
  - 设计我司商品库向量缓存与重建机制
  - 设计客户商品逐条召回 Top-K 策略
  - 设计召回结果记录结构
  - 定义召回失败与重试行为
- Deliverables：
  - 向量缓存方案
  - Top-K 召回方案
  - 召回评测方法
- Validation gate：
  在评测样本上，正确答案在 Top-K 中的召回率达到可接受水平，并能稳定复现。
- Risks：
  - 我司商品库重建向量成本较高
  - 文本拼装不合理会拖低召回效果
- Rollback or fallback：
  若 Top20 成本过高，可先用 Top10 验证；若召回明显不足，再扩回 Top20。

### Phase 4 - 主裁决与疑难复核链路

- Goal：
  形成“主裁决模型 + 疑难复核模型”的最终判断机制。
- Why this phase exists：
  这是整条模型主导链路里最直接决定错配率的环节。
- Inputs required：
  - 候选召回结果
  - 裁决 JSON schema
  - 四级状态定义
- Tasks：
  - 定义主裁决 prompt
  - 定义主裁决输出 JSON
  - 定义复核触发条件
  - 定义裁决结果到四级状态的映射
  - 定义低置信度与冲突样本的处理逻辑
- Deliverables：
  - 主裁决契约
  - 复核触发规则
  - 四级状态映射表
- Validation gate：
  对同一批样本重复测试时，裁决输出结构稳定，且 `auto_matched` 精度满足目标。
- Risks：
  - 主裁决模型过于激进导致错配
  - 复核模型使用范围过大导致成本和延迟失控
- Rollback or fallback：
  若 `deepseek-reasoner` 成本过高，第一版先做按阈值触发，不做全量复核。

### Phase 5 - 审核体验与结果导出重构

- Goal：
  让审核人员真正看到“更少错误、更好解释”的结果，而不是只换了模型但审核体验没变。
- Why this phase exists：
  用户的核心诉求不是模型多高级，而是审核时别再看到大量明显错误候选。
- Inputs required：
  - 裁决结果
  - 备选候选摘要结构
  - 现有导出逻辑
- Tasks：
  - 设计审核结果展示字段
  - 设计导出 Excel 的新增列
  - 设计 `suggested` 与 `manual_review` 的候选摘要呈现方式
  - 设计错误、超时、结构化输出异常的提示方式
- Deliverables：
  - 新版审核展示结构
  - 新版导出字段结构
  - 异常提示规则
- Validation gate：
  审核人员可以快速看到推荐候选、备选候选、置信度和原因，而不是只看到一个模糊结论。
- Risks：
  - 导出信息过多导致 Excel 难读
  - 审核页面信息密度过高反而降低效率
- Rollback or fallback：
  第一版先保证“主候选 + 候选摘要 + 置信度 + 原因”四类关键信息，避免一次性塞入过多字段。

### Phase 6 - 真实数据验收与上线门

- Goal：
  用真实数据验证这次转型是否真的降低了错配风险，并决定默认上线策略。
- Why this phase exists：
  没有真实数据验收，模型路线很容易看起来聪明，但业务上并没有真正变好。
- Inputs required：
  - 评测样本
  - 全链路运行结果
  - 业务抽检反馈
- Tasks：
  - 对比旧版规则路线与新版模型路线
  - 抽查 `auto_matched` 精度
  - 统计 `suggested/manual_review` 的 Top3 候选召回
  - 调整 prompt、阈值和复核触发条件
  - 决定 `reasoner` 是否默认开启
- Deliverables：
  - 验收报告
  - 上线参数建议
  - 后续迭代清单
- Validation gate：
  达到需求文档中的验收标准草案，尤其是自动通过精度与审核候选质量目标。
- Risks：
  - 模型效果提升不及预期
  - 成本、耗时与效果之间需要重新平衡
- Rollback or fallback：
  若新版在验收集上未显著优于旧版，不默认替换旧链路，而是以灰度或实验模式继续迭代。

## Dependencies

- Dependency 1：
  百炼普通 API Key 与 DeepSeek API Key 可稳定使用。
- Dependency 2：
  目标机器具备可访问外部模型 API 的网络条件。
- Dependency 3：
  有一批可人工标注或已知答案的真实样本用于验收。
- Dependency 4：
  当前上传、字段映射、导出骨架继续保留，不另起炉灶重做 UI。

## Risks and Unknowns

- Risk 1：
  标准化模型把品牌、商品名、规格拆错位，会连锁影响召回和裁决。
- Risk 2：
  向量召回做得不好，会让后面再强的裁决模型也无用武之地。
- Risk 3：
  主裁决模型如果偏激进，会直接放大错配风险。
- Risk 4：
  本地直连 API Key 虽然适合 MVP，但长期仍存在安全与运维风险。
- Risk 5：
  如果没有真实评测集，这次架构转型可能缺少客观验收基线。

## Approval Gates

- Gate 1：
  确认 v0.2 需求文档冻结，可以正式按模型主导路线进入实施。
- Gate 2：
  确认模型分工方案：
  百炼做标准化与召回，DeepSeek 做裁决与复核。
- Gate 3：
  确认评测样本集与验收指标。
- Gate 4：
  确认第一版允许客户端 API Key 直连方式。
- Gate 5：
  确认真实数据验收通过后，是否默认替换旧规则链路。

## Recommended Next Step

- First execution slice：
  先完成 Phase 0 和 Phase 1，也就是“冻结评测口径 + 冻结模型调用与配置契约”。
- Why this slice comes first：
  因为这次转型的风险不在代码细节，而在目标与边界是否稳定。只有先把评测口径和模型分工冻住，后面的标准化、召回和裁决实现才不会反复返工。
