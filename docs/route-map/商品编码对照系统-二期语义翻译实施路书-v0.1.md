# 商品编码对照系统 - 二期语义翻译实施路书

- 版本：v0.1
- 日期：2026-04-18
- 状态：执行基线草案
- 对应需求：`docs/requirements/商品编码对照系统-需求文档-二期语义翻译-v0.1.md`
- 对应技术规格：`docs/planning/商品编码对照系统-二期技术执行规格-v0.1.md`
- 核心方向：大模型主导商品语义翻译，程序负责流程和留痕

## 1. 执行目标

二期执行目标不是修补一期产品。

二期要重新做一套以大模型为主力的商品语义翻译流程。

最终目标是让系统能够：

- 理解客户整条商品记录表达的商品身份
- 理解我司商品库中商品名称、描述、别名和分类表达的商品身份
- 判断双方是否表达同一业务商品
- 识别偏差、遗漏和风险
- 给出强自动落码、弱自动落码、建议落码、必须人工审核或未匹配
- 给出业务人员能看懂的解释
- 建立产品记忆系统，沉淀人工确认、客户习惯、商品语义、业务等价关系和失败案例

一句话：

**二期要先证明“大模型能可靠做商品语义翻译”，再决定产品和工程怎么落地。**

## 2. 执行原则

### 2.1 不沿用一期产品逻辑

一期产品逻辑不作为二期执行基线。

一期只作为历史教训和少量工具性能力参考。

执行过程中不得默认沿用：

- 一期固定字段标准化思路
- 一期本地候选召回作为主判断入口
- 一期结果分级口径
- 一期“模型在末端裁决”的产品结构
- 一期以匹配流程为中心的页面和交互逻辑

### 2.2 大模型做主力

二期中，大模型负责理解和判断。

大模型应承担：

- 整行语义理解
- 我司商品表达理解
- 商品身份判断
- 证据对齐
- 偏差和遗漏识别
- 风险分级
- 结果解释

程序负责：

- Excel 读取
- 字段整理
- 上下文拼装
- 大模型调用
- 结果保存
- 人工审核
- 历史关系沉淀
- 导出和日志

### 2.3 先验证，再产品化

二期不能一开始就大规模写代码。

必须先用真实样本验证：

- 大模型是否能正确理解客户记录
- 大模型是否能正确理解我司商品表达
- 大模型是否能区分表达差异和商品身份差异
- 大模型是否能识别必须人工审核的情况
- 输出解释是否能让业务人员看懂

如果验证不成立，不应进入产品化。

### 2.4 不追求全自动

二期不以“自动落码率最高”为目标。

二期优先级是：

1. 不误译
2. 不遗漏
3. 可解释
4. 可追溯
5. 在安全范围内提高自动化

## 3. 总体里程碑

### Milestone 0：二期口径冻结

冻结二期不沿用一期产品逻辑、大模型作为主力的方向。

### Milestone 1：验证样本表完成

从真实客户库和我司库中整理出可用于验证的大模型样本集。

### Milestone 2：大模型语义翻译输出契约完成

明确大模型每次应该输入什么、输出什么、如何解释。

### Milestone 3：大模型离线验证通过

用样本表验证大模型是否具备商品语义翻译能力。

### Milestone 4：二期最小产品原型完成

围绕大模型主流程形成最小可用产品原型。

### Milestone 5：人工审核与产品记忆系统完成

让人工确认、客户表达习惯、商品语义、业务等价关系和失败案例可以反向沉淀为产品记忆。

### Milestone 6：真实客户库试跑与复盘

用完整客户库试跑，统计误译、遗漏、人工审核和弱自动落码效果。

## 4. 阶段计划

## Phase 0 - 二期口径冻结

### Goal

把二期产品方向彻底从一期匹配产品中切出来。

### Why

如果不先冻结口径，后续很容易重新滑回一期逻辑。

尤其容易滑回：

- 名称相似度
- 字段标准化
- 固定权重
- 本地候选召回
- 模型末端裁决

### Tasks

- 确认一期产品逻辑不作为二期基线。
- 确认二期以大模型作为主力理解层。
- 确认程序只承担流程、数据和留痕。
- 确认二期第一目标是不误译、不遗漏。
- 确认二期不追求完全自动落码。

### Deliverables

- 已修订的二期需求文档
- 本实施路书
- 需求目录和路书目录索引

### Validation Gate

项目成员能清楚说出：

**二期不是一期匹配产品升级，而是大模型主导的商品语义翻译产品。**

### Risks

- 讨论时继续借用一期术语，导致方向混乱。
- 工程实现时为了省事复用一期流程。

### Fallback

如果出现争议，优先回到二期需求文档中的总原则：

**大模型负责理解和判断，程序负责流程和留痕。**

## Phase 1 - 二期验证样本表

### Goal

建立一份真实、可验证、可复盘的二期样本表。

### Why

没有样本表，就无法判断大模型是否真的能翻译商品语义。

只靠感觉讨论，会很容易把“看起来合理”误认为“业务正确”。

### Inputs

- `我司商品库.xlsx`
- `客户商品库.xlsx`
- 二期需求文档
- 二期判断准绳文档

### Sample Coverage

样本表至少覆盖：

- 完全同名商品
- 名称不同但业务等价商品
- 同名不同规格商品
- 同名不同包装商品
- 品牌缺失商品
- 品牌冲突商品
- 系列或等级词商品
- 备注改变身份商品
- 名称中隐藏规格商品
- 规格列为空商品
- 多候选难区分商品
- 无法匹配商品

### Suggested Columns

样本表建议包含：

- 样本编号
- 客户原始商品名称
- 客户规格
- 客户单位
- 客户类别
- 客户备注
- 客户其他字段
- 我司候选商品编码
- 我司候选商品名称
- 我司规格
- 我司单位
- 我司描述
- 人工确认正确结果
- 人工判断理由
- 核心身份信号
- 强约束信号
- 弱约束信号
- 噪声或展示词
- 是否有偏差风险
- 是否有遗漏风险
- 期望结果分级
- 是否允许自动落码
- 不允许自动落码原因

### Tasks

- 从客户库中抽取第一批 100 条样本。
- 对每条样本人工查找可能对应的我司商品。
- 标注正确结果或标记无匹配。
- 标注每条样本的关键语义信号。
- 标注期望分级。
- 挑出 20 条特别困难样本作为压力测试集。

### Deliverables

- 二期验证样本表 v0.1
- 困难样本集 v0.1
- 样本标注规则说明

### Validation Gate

同一条样本，业务人员能解释：

- 为什么这个是正确商品
- 哪些信息不能丢
- 哪些差异可以接受
- 为什么可以或不能自动落码

### Risks

- 样本过少，无法覆盖真实复杂度。
- 样本只挑简单商品，导致验证虚高。
- 人工标注口径不一致。

### Fallback

如果一次性标 100 条太重，先做 30 条黄金样本。

但这 30 条必须覆盖简单、复杂、冲突和无法匹配场景。

## Phase 2 - 大模型输入输出契约

### Goal

定义大模型在二期中的输入、输出和解释格式。

### Why

大模型要做主力，必须让它输出可控结构。

不能只让模型自然语言回答“我觉得是这个”。

### Inputs

- 二期验证样本表
- 二期需求文档
- 商品语义信号定义

### Model Input Requirements

输入应至少包含：

- 客户整行原始记录
- 字段名和字段值
- 我司候选商品列表
- 每个候选的名称、编码、单位、描述、分类
- 已知业务等价关系
- 历史确认关系
- 本次任务要求

### Model Output Requirements

输出应为结构化 JSON。

建议字段包括：

```json
{
  "customer_semantic_summary": "",
  "key_identity_signals": [],
  "strong_constraints": [],
  "weak_constraints": [],
  "ignored_or_noise_signals": [],
  "missing_or_uncertain_signals": [],
  "candidate_assessments": [],
  "selected_candidate": null,
  "result_status": "",
  "risk_flags": [],
  "evidence_summary": "",
  "manual_review_reason": "",
  "can_auto_code": false
}
```

### Result Status

结果状态建议使用：

- `strong_auto_code`
- `weak_auto_code`
- `suggested_code`
- `manual_review`
- `unmatched`

### Tasks

- 起草客户记录理解 prompt。
- 起草我司候选证据对齐 prompt。
- 起草最终输出 JSON schema。
- 用 10 条黄金样本手工测试输出格式。
- 检查模型是否擅自脑补。
- 检查模型是否遗漏规格、包装、备注等信息。

### Deliverables

- 大模型输入模板 v0.1
- 大模型输出 JSON schema v0.1
- Prompt 草案 v0.1
- 10 条样本测试结果

### Validation Gate

模型输出必须满足：

- 结构稳定
- 能解释关键证据
- 能识别不确定信息
- 不把客户没写的信息当事实
- 不把必须人工的样本强行自动落码

### Risks

- 模型输出 JSON 不稳定。
- 模型为了给答案而脑补。
- 模型解释看起来合理但证据不足。

### Fallback

如果一次输出太复杂，可拆成两步：

1. 先让模型理解客户记录。
2. 再让模型对齐候选并裁决。

但仍然保持“大模型主导理解和判断”的方向。

## Phase 3 - 大模型候选池策略

### Goal

设计适合大模型判断的我司候选池机制。

### Why

大模型不能无限制读取整个商品库。

但二期也不能照搬一期的字符串候选召回。

候选池必须服务于语义翻译，而不是只服务于相似度。

### Candidate Pool Principles

候选池应尽量：

- 不漏掉语义等价候选
- 保留同义词候选
- 保留规格相近但可能不同的候选
- 保留品牌缺失但品名强相关的候选
- 保留可能存在系列、等级差异的候选
- 避免只因名称不相似就丢掉候选

### Candidate Pool Sources

候选来源可包括：

- 品名包含关系
- 品牌匹配
- 规格匹配
- 单位匹配
- 类别辅助
- 历史确认关系
- 业务等价关系
- 大模型对客户记录生成的搜索关键词

### Tasks

- 定义候选池最大数量。
- 定义候选池必须包含的信息字段。
- 测试 30 条样本的候选池覆盖率。
- 统计正确商品是否进入候选池。
- 标注未进入候选池的原因。
- 调整候选池生成策略。

### Deliverables

- 候选池策略 v0.1
- 候选池字段清单
- 候选池覆盖率测试报告

### Validation Gate

黄金样本中，正确商品应尽量进入候选池。

候选池不能只看字面相似。

### Risks

- 候选池太小，漏掉正确商品。
- 候选池太大，模型上下文过长。
- 候选池仍然退化成一期字符串召回。

### Fallback

如果程序候选池覆盖率不够，应允许大模型先生成搜索意图和关键词，再由程序二次检索。

## Phase 4 - 证据对齐与风险分级

### Goal

让大模型不仅给结果，还能说明证据和风险。

### Why

二期的核心不是“答案”，而是“答案为什么可靠”。

如果模型不能解释证据，人工审核仍然无法信任系统。

### Evidence Alignment Dimensions

证据对齐至少包括：

- 核心品名
- 品牌
- 系列或等级
- 规格
- 包装层级
- 单位
- 形态或加工方式
- 鲜冻状态
- 类别辅助
- 备注信息
- 我司商品描述

### Risk Flags

风险标记至少包括：

- `core_name_uncertain`
- `brand_conflict`
- `spec_conflict`
- `package_conflict`
- `unit_conflict`
- `series_or_grade_conflict`
- `remark_changes_identity`
- `needs_unstated_assumption`
- `multiple_valid_candidates`
- `insufficient_customer_info`
- `candidate_pool_missing_evidence`

### Tasks

- 定义证据对齐字段。
- 定义风险标记字典。
- 用困难样本测试风险识别。
- 检查模型是否能说明“为什么必须人工”。
- 检查模型是否能区分表达差异和身份差异。

### Deliverables

- 证据对齐结构 v0.1
- 风险标记字典 v0.1
- 困难样本风险识别报告

### Validation Gate

模型必须能明确说明：

- 哪些证据支持匹配
- 哪些证据缺失
- 哪些证据冲突
- 为什么自动落码或为什么人工审核

### Risks

- 模型解释过于笼统。
- 模型用好听的话掩盖证据不足。
- 风险标记过多导致审核人员看不懂。

### Fallback

如果风险标记太复杂，第一版只保留最高频、最危险的 6 到 8 类风险。

## Phase 5 - 二期最小产品原型

### Goal

基于已验证的大模型流程，做一个最小可用产品原型。

### Why

只有样本验证通过后，才值得产品化。

原型目标是验证完整操作链路，不是追求界面完整。

### Prototype Scope

最小原型应包含：

- 导入客户库
- 导入我司库
- 字段选择或自动识别
- 选择样本行或批量行
- 调用大模型语义翻译
- 展示候选证据对齐
- 展示风险和结果分级
- 人工确认或修正
- 导出结果

### Not In Scope

第一版原型不做：

- 复杂权限
- 多人协同审核
- 云端部署
- 完整规则管理后台
- 大规模性能优化
- 完整历史数据分析看板

### Tasks

- 设计原型页面流程。
- 定义每个页面展示字段。
- 定义模型调用入口。
- 定义结果保存格式。
- 定义导出列。
- 用 30 条样本跑通端到端流程。

### Deliverables

- 二期最小产品原型说明
- 页面流程草图或文字说明
- 端到端样本试跑结果

### Validation Gate

业务人员能完成：

1. 导入数据。
2. 看懂模型判断。
3. 确认或修正结果。
4. 导出结果。

### Risks

- 原型过早追求功能完整，拖慢验证。
- 页面沿用一期结构，导致产品逻辑回退。

### Fallback

如果页面原型来不及，先用离线表格加脚本跑通模型流程。

## Phase 6 - 人工审核与产品记忆系统

### Goal

让人工审核结果和模型失败经验成为系统下一次判断的有效资产。

### Why

二期不是一次性翻译。

系统应随着人工确认、客户习惯识别和失败案例复盘，逐渐积累客户语言和我司语言之间的稳定关系。

### Review Actions

人工审核至少支持：

- 确认系统推荐
- 改选其他候选
- 标记无匹配
- 标记模型理解错误
- 标记遗漏信息
- 补充业务等价关系
- 标记可用于弱自动落码

### Product Memory Types

产品记忆系统至少包括：

- 人工确认记忆
- 客户表达习惯记忆
- 商品语义记忆
- 业务等价关系记忆
- 失败案例记忆

### Manual Confirmation Memory Fields

人工确认记忆建议包含：

- 客户原始表达
- 客户字段快照
- 我司商品编码
- 我司商品名称
- 确认人
- 确认时间
- 确认理由
- 适用条件
- 是否可用于弱自动落码
- 是否需要定期复核

### Failure Memory Fields

失败案例记忆建议包含：

- 原客户记录
- 模型原判断
- 人工纠正结果
- 错误类型
- 错误原因
- 后续应新增的风险提示
- 是否需要调整 Prompt
- 是否需要调整候选池

### Tasks

- 定义人工审核动作。
- 定义产品记忆系统数据结构。
- 定义人工确认记忆数据结构。
- 定义客户表达习惯记忆数据结构。
- 定义商品语义记忆数据结构。
- 定义失败案例记忆数据结构。
- 定义业务等价关系维护方式。
- 定义历史关系和当前证据冲突时的处理。
- 测试弱自动落码是否能引用历史关系并留痕。

### Deliverables

- 人工审核动作清单
- 产品记忆系统结构 v0.1
- 人工确认记忆结构 v0.1
- 失败案例记忆结构 v0.1
- 业务等价关系结构 v0.1

### Validation Gate

系统必须能说明：

- 本次结果是否引用历史关系
- 引用了哪条产品记忆
- 当前记录是否仍满足记忆适用条件
- 是否存在失败案例记忆触发的风险收紧

### Risks

- 错误人工确认被沉淀为规则。
- 历史关系无条件覆盖当前证据。
- 模型自己猜测的内容被错误写入长期记忆。
- 客户表达习惯被错误套用到其他客户。

### Fallback

第一版产品记忆只作为提示，不直接自动落码。

等样本验证稳定后，再开放弱自动落码。

## Phase 7 - 真实客户库试跑与复盘

### Goal

用真实客户库验证二期方案是否能降低误译和遗漏。

### Why

样本验证只能证明方向可行。

真实客户库试跑才能暴露规模、格式、噪声和业务边界问题。

### Metrics

试跑应统计：

- 强自动落码数量
- 弱自动落码数量
- 建议落码数量
- 必须人工审核数量
- 未匹配数量
- 抽检错误自动落码数量
- 偏差数量
- 遗漏数量
- 候选池漏召回数量
- 人工审核平均耗时

### Tasks

- 选择一份真实客户库试跑。
- 抽检强自动和弱自动结果。
- 重点复查人工审核样本。
- 汇总偏差和遗漏类型。
- 调整 prompt、候选池和风险标记。
- 决定是否进入正式产品开发。

### Deliverables

- 真实客户库试跑报告
- 偏差和遗漏问题清单
- 下一版需求修订建议
- 是否进入产品化的判断

### Validation Gate

如果强自动和弱自动结果不能被业务接受，不进入正式产品化。

如果人工审核仍然不能明显省力，需要回到 Phase 2 到 Phase 4 调整大模型流程。

### Risks

- 真实数据复杂度超过样本预期。
- 大模型成本或速度不可接受。
- 输出解释仍不够业务可读。

### Fallback

先把二期定位为“审核辅助翻译器”，暂缓自动落码。

## 5. 执行顺序建议

建议严格按以下顺序执行：

1. 冻结二期口径。
2. 做验证样本表。
3. 做大模型输入输出契约。
4. 用样本离线测试大模型。
5. 做候选池策略。
6. 做证据对齐和风险分级。
7. 做最小产品原型。
8. 做人工审核和历史关系沉淀。
9. 用真实客户库试跑。
10. 决定是否进入正式产品化。

不要跳过样本验证直接写产品。

不要为了复用一期代码而倒推产品流程。

## 6. 当前最小下一步

当前最小下一步不是写代码。

当前最小下一步是：

**制作二期验证样本表 v0.1。**

建议先做 30 条黄金样本。

这 30 条样本必须包含：

- 简单可自动样本
- 表达差异样本
- 规格冲突样本
- 包装冲突样本
- 品牌缺失样本
- 备注改变身份样本
- 多候选样本
- 无匹配样本

完成后，再用这些样本测试大模型能否稳定输出：

- 客户语义理解
- 关键证据
- 候选对齐
- 风险提示
- 分级结果
- 是否可自动落码

## 7. 总结

二期执行的关键不是“快点做一个新系统”。

真正关键是先证明：

**大模型能否可靠承担商品语义翻译主力。**

如果能证明，再产品化。

如果不能证明，就不能贸然把它包装成自动编码工具。

这条路比一期更慢一点，但更稳。

它避免继续在失败产品逻辑上修补，也更接近真实业务问题。
