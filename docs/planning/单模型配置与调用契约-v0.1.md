# 单模型配置与调用契约 v0.1

- 版本：v0.1
- 日期：2026-03-28
- 状态：当前有效
- 对应主线：单模型生产方案

## 1. 目的

本文件用于把当前单模型生产方案落成可直接实现的技术契约，避免后续实现时把模型、密钥、设置页字段和读取逻辑写散。

一句话：
把“默认推荐千问，但模型和密钥都走配置”落成一套可执行规格。

## 2. 当前结论

当前主线固定为：

- 默认推荐提供方：阿里云百炼
- 默认推荐模型：`qwen-plus`
- 生产主链路：单模型标准化 + 本地候选召回 + 单模型裁决
- 生产模型必须可配置
- 真实 API Key 不允许写入源码、模板文件或提交到仓库

## 3. 适用范围

适用于：

- 第一版生产主链路
- Windows 本地运行场景
- Web 本地服务和桌面客户端壳

不适用于：

- 多模型生产协同
- 向量召回生产链路
- Coding Plan key 调用

## 4. 核心原则

### 4.1 模型可配置

- 生产模型必须是配置项
- 默认推荐值是 `qwen-plus`
- 默认推荐不等于代码写死

### 4.2 一个生产模型，两类任务

同一个生产模型承担两类任务：

- 标准化
- 裁决

程序只负责：

- 配置读取
- 请求组装
- 候选缩圈
- 结果校验
- 错误提示
- 日志记录

### 4.3 API Key 不进源码

- 真实 API Key 不允许写入 Python 源码
- 真实 API Key 不允许写入前端模板
- 真实 API Key 不允许写入会被提交到仓库的默认配置文件

## 5. 配置文件策略

### 5.1 仓库内只保留样例文件

仓库中允许存在：

- `config/model_settings.example.json`

这个文件只放占位符和默认推荐值，不放真实密钥。

### 5.2 真实运行配置文件

真实运行配置建议使用：

- `<DATA_ROOT>/config/model_settings.json`

其中 `DATA_ROOT` 的来源与程序运行方式一致：

- 若设置了 `PRODUCT_MATCHER_DATA_DIR`，则使用该目录
- 若为桌面打包环境，则使用本地应用数据目录
- 若为开发态且 `DATA_ROOT` 仍指向项目根目录，则默认推荐使用环境变量，不推荐把真实密钥保存到仓库工作区

### 5.3 当前实现建议

第一版实现建议如下：

- 开发态优先使用环境变量
- 设置页允许本地保存配置
- 如果未来允许“保存真实 API Key 到本地文件”，保存目标必须是运行时数据目录，而不是仓库默认样例文件

## 6. 模型配置结构

第一版建议采用单文件结构，字段如下：

- `version`
- `provider_name`
- `base_url`
- `production_model_name`
- `api_key_source`
- `api_key_env_name`
- `api_key_value`
- `timeout_seconds`
- `max_retries`

字段说明：

- `version`
  配置结构版本号，便于后续升级
- `provider_name`
  当前默认推荐值：`bailian`
- `base_url`
  当前默认推荐值：百炼兼容接口地址
- `production_model_name`
  当前默认推荐值：`qwen-plus`
- `api_key_source`
  允许值：
  - `env`
  - `local_config`
- `api_key_env_name`
  当 `api_key_source=env` 时使用
- `api_key_value`
  当 `api_key_source=local_config` 时使用
- `timeout_seconds`
  模型请求超时秒数
- `max_retries`
  单次请求失败后的最大重试次数

## 7. 配置样例

建议样例如下：

```json
{
  "version": 1,
  "provider_name": "bailian",
  "base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1",
  "production_model_name": "qwen-plus",
  "api_key_source": "env",
  "api_key_env_name": "DASHSCOPE_API_KEY",
  "api_key_value": "",
  "timeout_seconds": 60,
  "max_retries": 2
}
```

说明：

- 样例文件中 `api_key_value` 必须为空
- 默认推荐值允许直接出现在样例文件里
- 真实密钥只允许出现在本地运行配置或环境变量中

## 8. 设置页字段

第一版设置页建议只放最小必需字段：

- `模型提供方`
  - 类型：下拉
  - 必填：是
  - 默认值：`阿里云百炼`
- `Base URL`
  - 类型：文本输入
  - 必填：是
  - 默认值：百炼兼容接口地址
- `生产模型名`
  - 类型：文本输入或下拉
  - 必填：是
  - 默认值：`qwen-plus`
- `API Key 来源`
  - 类型：单选
  - 必填：是
  - 允许值：`环境变量` / `本地保存`
- `环境变量名`
  - 类型：文本输入
  - 显示条件：`API Key 来源=环境变量`
  - 默认值：`DASHSCOPE_API_KEY`
- `API Key`
  - 类型：密码输入
  - 显示条件：`API Key 来源=本地保存`
  - 默认值：空
- `请求超时（秒）`
  - 类型：数字输入
  - 必填：是
  - 默认值：`60`
- `失败重试次数`
  - 类型：数字输入
  - 必填：是
  - 默认值：`2`

### 8.1 设置页按钮

第一版建议有以下按钮：

- `保存配置`
- `测试连接`
- `恢复推荐值`

### 8.2 设置页交互约束

- 当 `API Key 来源=环境变量` 时，隐藏 `API Key` 输入框
- 当 `API Key 来源=本地保存` 时，隐藏 `环境变量名`
- 已保存的本地 API Key 不应回显原文
- 如果本地 API Key 已存在，编辑页面只显示“已保存”状态和遮罩提示
- 若用户未重新输入新 key，保存时应保留原值而不是清空
- 如需清空已保存 key，应提供明确动作，不应通过“空输入保存”隐式清除

## 9. 配置读取方式

第一版不建议做隐式优先级覆盖，而是走“来源显式决策”。

读取步骤如下：

1. 载入默认推荐值
2. 读取本地运行配置文件
3. 根据 `api_key_source` 决定实际取值来源
4. 校验是否满足调用条件
5. 生成运行时配置对象

### 9.1 当 `api_key_source=env`

读取逻辑：

1. 读取 `api_key_env_name`
2. 从环境变量中取值
3. 若环境变量不存在或为空，返回显式错误

### 9.2 当 `api_key_source=local_config`

读取逻辑：

1. 读取 `api_key_value`
2. 若为空，返回显式错误
3. 若有值，直接作为当前运行 key

### 9.3 不允许的读取方式

- 不允许在 `app.py` 中直接定义真实 key 常量
- 不允许从前端隐藏字段回传长期保存的 key
- 不允许从仓库内样例配置直接读取真实 key

## 10. 运行时配置对象

程序内部建议统一整理为一个运行时对象，至少包含：

- `provider_name`
- `base_url`
- `production_model_name`
- `api_key`
- `timeout_seconds`
- `max_retries`

这个对象是后续标准化和裁决两个任务共享的唯一模型配置入口。

## 11. 配置校验规则

保存配置时至少校验：

- `provider_name` 不为空
- `base_url` 不为空
- `production_model_name` 不为空
- `timeout_seconds` 必须大于 `0`
- `max_retries` 不能小于 `0`
- 若 `api_key_source=env`，则 `api_key_env_name` 不为空
- 若 `api_key_source=local_config`，则 `api_key_value` 不为空或已有本地旧值

运行前至少校验：

- 已成功解析到真实 `api_key`
- `base_url` 合法
- `production_model_name` 合法

## 12. 设置页错误提示建议

建议使用明确错误，不要模糊失败：

- `未配置模型提供方`
- `未配置 Base URL`
- `未配置生产模型名`
- `未读取到环境变量 API Key`
- `未保存本地 API Key`
- `模型连接测试失败`
- `配置已保存，但连接测试未通过`

## 13. 标准化调用契约

### 13.1 输入结构

标准化阶段至少需要这些输入字段：

- 原始商品编码
- 原始商品名称
- 原始品牌
- 原始规格
- 原始单位
- 原始分类
- 来源标记

### 13.2 输出结构

标准化阶段至少输出：

- `brand_std`
- `product_std`
- `spec_std`
- `package_std`
- `unit_std`
- `category_std`
- `alias_notes`
- `normalize_confidence`
- `raw_snapshot`

### 13.3 要求

- 输出必须是稳定 JSON
- 原始字段必须保留
- 结构化输出失败时必须显式报错

## 14. 本地候选召回契约

### 14.1 输入依据

本地候选召回至少参考：

- 原始商品名称
- `product_std`
- `brand_std`
- `spec_std`
- `unit_std`
- `alias_notes`

### 14.2 输出结构

每条客户商品至少输出：

- `candidate_refs`
- `candidate_count`
- `recall_notes`

### 14.3 约束

- 召回层只负责缩小候选范围
- 召回层不负责最终判断是否同商品
- 召回结果必须可追溯

## 15. 裁决调用契约

### 15.1 输入结构

裁决阶段输入为：

- 当前客户商品原始信息
- 当前客户商品标准化结果
- 候选集合摘要

### 15.2 输出结构

裁决阶段至少输出：

- `match_status`
- `selected_candidate_ref`
- `confidence`
- `summary`
- `reasons`
- `risk_flags`
- `candidate_rankings`

### 15.3 状态约束

`match_status` 只能是：

- `auto_matched`
- `suggested`
- `manual_review`
- `unmatched`

## 16. 后续演进边界

后续允许扩展：

- 向量召回实验
- 第二模型 challenger 实验
- 更安全的密钥存储

后续扩展原则：

- 不破坏单模型主链路
- 不把真实密钥重新引回源码

## 17. 当前结论

当前项目在技术实现上必须坚持这四件事：

- 默认推荐千问，但模型可配置
- API Key 走本地读取，不进源码
- 设置页字段只保留单模型 MVP 所需最小集合
- 单模型承担标准化和裁决，程序负责候选缩圈和流程控制
