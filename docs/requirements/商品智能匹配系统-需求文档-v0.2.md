# 商品智能匹配系统 - 需求文档

- 版本：v0.2
- 日期：2026-03-27
- 状态：已确认，可进入实施路书阶段
- 对应方向：从“规则优先、AI 可选增强”调整为“模型主导、程序管流程”

## 1. 问题定义

- 目标：
  构建一个运行在 Windows 本地环境中的商品匹配工具，用于把“客户商品库”和“我司商品库”进行高质量对照，重点目标是尽量少错配，而不是单纯追求自动通过率。
- 主要使用人：
  采购人员、销售支持、商品资料维护人员、需要做客户商品对照的内部运营人员。
- 用户价值：
  降低人工逐条比对成本，同时让人工审核看到的候选更准确、更少明显错误。

## 2. 已确认范围

### 2.1 In Scope

- 上传两份 Excel：
  我司商品库与客户商品库。
- 字段对照：
  用户在页面中完成两份 Excel 到标准字段的映射。
- 模型主导标准化：
  使用大模型对品牌、核心商品名、规格、包装层级、单位、分类进行结构化抽取与归一。
- 向量召回：
  使用向量模型先从我司商品库中召回候选集合。
- 模型最终裁决：
  使用裁决模型对候选进行判定并输出结构化结果。
- 分级结果输出：
  输出 `auto_matched`、`suggested`、`manual_review`、`unmatched` 四类结果。
- 人工审核友好输出：
  在系统界面和导出结果中展示主候选、备选候选、置信度、原因说明。
- 本地运行：
  工具仍以 Windows 本地客户端/本地服务方式运行。
- API Key 配置：
  在软件内通过 API Key 直连国内模型服务。

### 2.2 Out of Scope

- 不以规则引擎作为主判断路径。
- 不继续把大量业务知识硬编码成复杂规则树。
- 不做公有云 SaaS 平台。
- 不做完全离线匹配。
- 不追求“无人工审核”的全自动通过。
- 不使用阿里云 Coding Plan `sk-sp-...` 作为本系统后端调用方式。
- 第一版不做模型精调、私有知识库训练、复杂审批流。

## 3. 核心业务目标

### 3.1 第一优先级

- 尽量少错配。
- 自动通过的结果必须非常保守。
- 即使仍保留人工审核，也要尽量减少“审核时看到很多明显错误候选”的情况。

### 3.2 第二优先级

- 降低人工审核量。
- 提高审核效率。
- 让审核人员能快速理解模型为什么推荐某个候选。

### 3.3 非目标

- 不是为了把所有商品都变成自动匹配。
- 不是为了追求大模型全权接管，不可解释地直接拍板。

## 4. 产品定位

- 形态：
  Windows 本地运行工具。
- 网络依赖：
  上传、预览、字段映射等本地流程可在本机完成；标准化、召回、裁决阶段依赖外部模型 API。
- AI 角色：
  AI 是主判断引擎，程序负责流程控制、数据组织、日志、导出与审核闭环。
- 交付方式：
  第一版允许直接在客户端中配置 API Key 并调用模型。

## 5. 模型分工方案

## 5.1 总体原则

- 不使用单一模型包打天下。
- 按能力分工，而不是按厂商情绪选型。
- 程序负责把问题拆成多个稳定子任务，再交给不同模型处理。

## 5.2 第一版建议分工

- 模型 A：标准化模型
  - 提供方：阿里云百炼
  - 建议模型：`qwen-plus`
  - 任务：抽取并归一品牌、商品主词、规格、包装、单位、分类、别名说明。
- 模型 B：召回模型
  - 提供方：阿里云百炼
  - 建议模型：`text-embedding-v4`
  - 任务：将标准化后的商品文本向量化，用于从我司商品库中召回 Top-K 候选。
- 模型 C：主裁决模型
  - 提供方：DeepSeek
  - 建议模型：`deepseek-chat`
  - 任务：对候选进行匹配判断并输出结构化决策。
- 模型 D：疑难复核模型
  - 提供方：DeepSeek
  - 建议模型：`deepseek-reasoner`
  - 任务：仅处理高风险、低置信度或 Top1/Top2 接近的难例。

## 5.3 为什么这样分工

- `qwen-plus` 更适合做结构化抽取和字段归一。
- `text-embedding-v4` 适合做中文商品语义召回。
- `deepseek-chat` 适合做大批量裁决，兼顾成本和结构化输出。
- `deepseek-reasoner` 只处理难例，避免全面使用导致成本和延迟失控。

## 6. 主流程

1. 上传我司商品库 Excel。
2. 上传客户商品库 Excel。
3. 系统读取表头并展示字段对照表。
4. 用户确认标准字段映射。
5. 系统对我司商品库进行标准化并缓存结果。
6. 系统对客户商品库进行标准化。
7. 系统基于向量召回从我司商品库中取每条客户商品的 Top-K 候选。
8. 系统用主裁决模型对候选进行匹配判断。
9. 对疑难样本再调用复核模型。
10. 系统输出分级结果、理由、置信度、候选摘要。
11. 用户查看审核结果并导出新 Excel。

## 7. 功能需求

### 7.1 Excel 导入与字段映射

- 仅要求第一版稳定支持 `.xlsx`。
- 标准字段至少包含：
  - 商品编码
  - 商品名称
  - 品牌
  - 规格
  - 单位
  - 分类
- 字段映射需支持模板复用。
- 若关键字段缺失，系统必须明确提示后续影响。

### 7.2 标准化需求

- 标准化阶段必须产出统一结构，而不是只保留原始商品名称。
- 每条商品至少生成以下字段：
  - `brand_std`
  - `product_std`
  - `spec_std`
  - `package_std`
  - `unit_std`
  - `category_std`
  - `alias_notes`
  - `normalize_confidence`
- 标准化必须保留原始值，便于人工追溯。
- 模型输出必须是稳定 JSON，不能依赖自然语言段落解析。

### 7.3 召回需求

- 系统不能让裁决模型直接面对整库商品。
- 必须先召回候选集合，再做裁决。
- 第一版默认召回范围建议为 Top 20。
- 召回文本应优先基于标准化后的核心字段，而不是原始整串名称。
- 我司商品库的向量结果应支持本地缓存，避免每次重复重算。

### 7.4 裁决需求

- 裁决模型必须对单条客户商品 + 候选集合输出结构化 JSON。
- 裁决输出至少包含：
  - `match_status`
  - `selected_candidate_ref`
  - `confidence`
  - `summary`
  - `reasons`
  - `risk_flags`
- `match_status` 只能是：
  - `auto_matched`
  - `suggested`
  - `manual_review`
  - `unmatched`
- 裁决必须优先服务于“少错配”，不以提升自动通过率为第一目标。

### 7.5 疑难复核需求

- 以下情况允许升级到复核模型：
  - 主裁决置信度低
  - Top1 与 Top2 差距很小
  - 品牌、规格、包装层级存在明显歧义
  - 商品名包含大量别名、简称或行业口语
- 复核模型不面向全量数据，只处理疑难样本。

### 7.6 人工审核需求

- 人工审核不会被取消。
- 审核页面或审核导出中必须看到：
  - 当前推荐候选
  - 备选候选摘要
  - 置信度
  - 模型理由
  - 原始商品信息
  - 标准化结果
- 审核目标不是重新找候选，而是快速确认或修正模型建议。

### 7.7 结果导出需求

- 结果导出基于客户原始 Excel 生成新文件，不覆盖原文件。
- 至少追加以下列：
  - 匹配状态
  - 置信度
  - 我司商品编码
  - 我司商品名称
  - 我司品牌
  - 我司规格
  - 我司单位
  - 我司分类
  - 匹配说明
  - 候选摘要
  - 审核状态
  - 审核备注
- 对于 `manual_review` 和 `unmatched`，不能假装回填一个确定结果。

### 7.8 配置需求

- 第一版允许在本地配置：
  - 百炼 Base URL
  - 百炼 API Key（普通 `sk-...`）
  - 标准化模型名
  - Embedding 模型名
  - DeepSeek Base URL
  - DeepSeek API Key
  - 主裁决模型名
  - 复核模型名
- Coding Plan `sk-sp-...` 不纳入本系统支持范围。

## 8. 数据输入、输出与外部依赖

### 8.1 输入

- 我司商品库 Excel
- 客户商品库 Excel
- 字段映射配置
- 百炼 API Key
- DeepSeek API Key

### 8.2 输出

- 标准化后的商品结构数据
- 候选召回结果
- 模型裁决结果
- 审核导出 Excel
- 匹配日志与错误日志

### 8.3 外部系统

- 阿里云百炼通用 API
- DeepSeek API

## 9. 约束条件

### 9.1 技术约束

- 模型必须使用国内主流服务。
- 第一版采用 API Key 直连，不走自建中转服务。
- 第一版不使用 Coding Plan key。
- 模型必须支持稳定的结构化输出。

### 9.2 业务约束

- 自动通过必须极度保守。
- 人工审核仍是正式流程的一部分。
- 系统要尽量减少“明显不对的候选进入审核列表”的情况。

### 9.3 运行约束

- 运行环境以 Windows 本地为主。
- 模型调用阶段要求网络可用。
- 第一版允许内部受控环境直接保存和使用 API Key。

## 10. MVP 范围

- 双 Excel 上传
- 字段对照与模板复用
- 百炼模型标准化
- 百炼 Embedding 召回
- DeepSeek 主裁决

- 四级结果输出
- 审核友好导出

- 运行日志与错误日志

## 11. 验收标准草案

- 验收标准 1：
  使用有效的百炼与 DeepSeek API Key，系统可完成“上传 -> 字段对照 -> 标准化 -> 候选召回 -> 模型裁决 -> Excel 导出”全流程。
- 验收标准 2：
  每条客户商品都必须得到一个明确的 `match_status`，且输出结构化说明。
- 验收标准 3：
  `auto_matched` 结果必须带有明确置信度和原因说明。
- 验收标准 4：
  `manual_review` 与 `unmatched` 结果不得伪装成已确认匹配。
- 验收标准 5：
  审核人员能看到推荐候选与备选候选摘要，而不是只看到一个模糊结果。
- 验收标准 6：
  在一组人工标注验证样本上，`auto_matched` 的精度目标应达到 98% 以上。
- 验收标准 7：
  在同一组验证样本上，`suggested + manual_review` 的 Top3 候选召回目标应达到 90% 以上。
- 验收标准 8：
  当模型调用失败、超时或结构化输出异常时，系统必须给出显式错误，不允许静默写入错误匹配结果。

## 12. 假设

- 假设 1：
  第一版优先服务内部或受控客户环境，允许通过 API Key 直连模型。
- 假设 2：
  审核界面可分两阶段推进，第一阶段至少保证导出 Excel 可审核，第二阶段再补更完整的审核页。
- 假设 3：
  我司商品库规模在第一版可接受的向量化与缓存范围内。
- 假设 4：
  第一版不做模型微调，而是通过任务拆分、提示词与分级策略完成效果控制。

## 13. 当前仍需在实施阶段细化但不阻塞开工的问题

- 疑难复核模型默认开启还是按阈值触发。
- 审核结果回流是先写 Excel 还是先写本地数据库。
- 第一版是否在导出文件中展示完整 Top3 候选明细，还是只展示候选摘要。
- 本地 API Key 存储是否先用明文配置文件，还是第一版就接系统密钥库。
