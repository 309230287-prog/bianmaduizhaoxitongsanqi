# 商品智能匹配系统 - 需求文档

- 版本：v0.3
- 日期：2026-03-28
- 状态：已确认，可进入实施路书阶段
- 对应方向：从“多模型分工”收敛为“单模型生产主链路”

## 1. 问题定义

- 目标：
  构建一个运行在 Windows 本地环境中的商品匹配工具，用于把“客户商品库”和“我司商品库”进行高质量对照。第一目标是尽量少错配，第二目标是让人工审核看到更少明显错误的候选。
- 主要使用人：
  采购人员、销售支持、商品资料维护人员、需要做客户商品对照的内部运营人员。
- 用户价值：
  降低人工逐条比对成本，同时把审核工作从“自己重新找答案”变成“快速确认或修正系统建议”。

## 2. 已确认范围

### 2.1 In Scope

- 上传两份 Excel：
  我司商品库与客户商品库。
- 字段对照：
  用户在页面中完成两份 Excel 到标准字段的映射。
- 单模型标准化：
  使用同一个大模型对品牌、核心商品名、规格、包装层级、单位、分类进行结构化抽取与归一。
- 本地候选召回：
  程序根据原始字段和标准化字段，在我司商品库中缩小候选范围。
- 单模型最终裁决：
  仍使用同一个大模型，对候选集合做最终匹配判断并输出结构化结果。
- 分级结果输出：
  输出 `auto_matched`、`suggested`、`manual_review`、`unmatched` 四类结果。
- 人工审核友好输出：
  在系统界面和导出结果中展示主候选、备选候选、置信度、原因说明。
- 本地运行：
  工具仍以 Windows 本地客户端或本地服务方式运行。
- API Key 配置：
  在软件内通过本地配置读取 API Key，直连国内模型服务。

### 2.2 Out of Scope

- 第一版生产主链路不使用多模型协同。
- 第一版生产主链路不使用向量召回。
- 不以复杂规则引擎作为主判断路径。
- 不继续把大量业务知识硬编码成复杂规则树。
- 不做公有云 SaaS 平台。
- 不做完全离线匹配。
- 不追求“无人工审核”的全自动通过。
- 不使用阿里云 Coding Plan `sk-sp-...` 作为本系统后端调用方式。
- 第一版不做模型精调、私有知识库训练、复杂审批流。

## 3. 核心业务目标

### 3.1 第一优先级

- 尽量少错配。
- 自动通过的结果必须非常保守。
- 即使仍保留人工审核，也要尽量减少“审核时看到很多明显错误候选”的情况。

### 3.2 第二优先级

- 降低人工审核量。
- 提高审核效率。
- 让审核人员能快速理解系统为什么推荐某个候选。

### 3.3 非目标

- 不是为了把所有商品都变成自动匹配。
- 不是为了追求“模型越多越高级”。
- 不是为了让程序端承担最终业务拍板。

## 4. 为什么当前选择 C 方案

- 现实约束：
  并不是所有目标电脑都能稳定接入多模型服务，因此正式生产链路需要尽量减少外部依赖。
- 部署约束：
  单模型方案只需要一套模型服务、一套 API Key、一条联网链路，更适合在不同机器上稳定运行。
- 口径一致性：
  标准化和裁决由同一个模型完成，更容易保证对品牌、商品名、规格、包装的理解口径一致。
- 排错与运维：
  出问题时更容易判断是“标准化问题”“本地召回问题”还是“裁决问题”，不会陷入多模型互相甩锅。
- 迭代路径：
  单模型主链路可以先跑稳，后续若需要再增加向量或第二模型，也是在稳定基础上增强，而不是一开始就把复杂度拉满。

## 5. 产品定位

- 形态：
  Windows 本地运行工具。
- 网络依赖：
  上传、预览、字段映射等本地流程可在本机完成；标准化和裁决阶段依赖外部模型 API。
- AI 角色：
  同一个模型负责“理解商品”和“裁决候选”，程序负责流程控制、候选缩圈、日志、导出与审核闭环。
- 交付方式：
  第一版允许直接在客户端中配置模型提供方、模型名和 API Key 并调用模型。

## 6. 单模型生产方案

### 6.1 生产模型

- 提供方：
  默认推荐阿里云百炼。
- 默认推荐模型：
  `qwen-plus`。
- 第一版原则：
  生产主链路只接一个模型服务，不引入第二模型作为正式依赖。
- 配置原则：
  生产模型为配置项，默认值推荐 `qwen-plus`，但不在代码中写死模型名或 API Key。

### 6.2 模型与程序分工

- 模型第一次调用：
  对我司商品和客户商品做标准化抽取与归一。
- 程序中间层：
  基于原始商品信息和标准化结果，在我司商品库中召回 Top-N 候选。
- 模型第二次调用：
  对“客户商品 + 候选集合”做最终裁决，输出结构化 JSON。
- 人工审核：
  对 `suggested`、`manual_review` 和需要复核的记录做确认或修正。

### 6.3 后续增强方向

- 向量召回可作为后续增强能力，但不进入第一版生产主链路。
- 第二模型可作为离线对比或 challenger 能力，但不进入第一版生产主链路。

## 7. 主流程

1. 上传我司商品库 Excel。
2. 上传客户商品库 Excel。
3. 系统读取表头并展示字段对照表。
4. 用户确认标准字段映射。
5. 系统用当前配置的生产模型对我司商品库进行标准化并缓存结果。
6. 系统用当前配置的生产模型对客户商品库进行标准化。
7. 系统根据原始字段和标准化字段，在我司商品库中为每条客户商品召回 Top-N 候选。
8. 系统再次调用当前配置的生产模型，对每条客户商品及其候选集合做最终裁决。
9. 系统输出分级结果、理由、风险提示和候选摘要。
10. 用户查看审核结果并导出新 Excel。

## 8. 功能需求

### 8.1 Excel 导入与字段映射

- 第一版稳定支持 `.xlsx`。
- 标准字段至少包含：
  - 商品编码
  - 商品名称
  - 品牌
  - 规格
  - 单位
  - 分类
- 字段映射需支持模板复用。
- 若关键字段缺失，系统必须明确提示后续影响。

### 8.2 标准化需求

- 标准化阶段必须产出统一结构，而不是只保留原始商品名称。
- 每条商品至少生成以下字段：
  - `brand_std`
  - `product_std`
  - `spec_std`
  - `package_std`
  - `unit_std`
  - `category_std`
  - `alias_notes`
  - `normalize_confidence`
- 标准化必须保留原始值，便于人工追溯。
- 模型输出必须是稳定 JSON，不能依赖自然语言段落解析。

### 8.3 本地候选召回需求

- 程序不能把整库商品直接交给模型裁决。
- 必须先把候选范围缩小，再由模型拍板。
- 第一版默认召回范围建议为 Top 10 到 Top 20。
- 召回输入应同时参考：
  - 原始商品名称
  - 标准化后的核心商品名
  - 品牌
  - 规格
  - 单位
  - 别名说明
- 召回层的职责只是“缩小范围”，不是“最终判断是否同商品”。
- 召回结果应保留候选来源或召回依据，便于排错。

### 8.4 单模型裁决需求

- 裁决模型必须对单条客户商品 + 候选集合输出结构化 JSON。
- 裁决输出至少包含：
  - `match_status`
  - `selected_candidate_ref`
  - `confidence`
  - `summary`
  - `reasons`
  - `risk_flags`
  - `candidate_rankings`
- `match_status` 只能是：
  - `auto_matched`
  - `suggested`
  - `manual_review`
  - `unmatched`
- 裁决必须优先服务于“少错配”，不以提升自动通过率为第一目标。

### 8.5 结果分级需求

- `auto_matched`：
  仅用于模型判断明确、无明显风险、且不需要人工再看一眼的结果。
- `suggested`：
  模型有较强倾向，但仍建议人工快速确认。
- `manual_review`：
  有可疑候选，但模型判断存在风险、冲突或不确定。
- `unmatched`：
  候选集合中没有足够可靠的匹配对象。

### 8.6 人工审核需求

- 人工审核不会被取消。
- 审核页面或审核导出中必须看到：
  - 当前推荐候选
  - 备选候选摘要
  - 置信度
  - 模型理由
  - 原始商品信息
  - 标准化结果
- 审核目标不是重新找候选，而是快速确认或修正系统建议。

### 8.7 结果导出需求

- 结果导出基于客户原始 Excel 生成新文件，不覆盖原文件。
- 至少追加以下列：
  - 匹配状态
  - 置信度
  - 我司商品编码
  - 我司商品名称
  - 我司品牌
  - 我司规格
  - 我司单位
  - 我司分类
  - 匹配说明
  - 候选摘要
  - 审核状态
  - 审核备注
- 对于 `manual_review` 和 `unmatched`，不能假装回填一个确定结果。

### 8.8 配置需求

- 第一版允许在本地配置：
  - 模型提供方
  - Base URL
  - API Key 名称或来源
  - API Key 值
  - 生产模型名
  - 请求超时
  - 重试次数
- 第一版默认推荐配置：
  - 百炼 Base URL
  - 百炼普通 API Key（普通 `sk-...`）
  - `qwen-plus`
- 配置要求：
  - API Key 只允许从本地配置、环境变量或后续安全存储中读取。
  - 不允许把真实 API Key 写入源码、默认配置文件或提交到仓库。
- 第一版不配置第二模型。
- Coding Plan `sk-sp-...` 不纳入本系统支持范围。

- API Key

### 9.2 输出

- 标准化后的商品结构数据
- 候选召回结果
- 模型裁决结果
- 审核导出 Excel

### 9.3 外部系统

## 10. 约束条件

### 10.1 技术约束

- 模型必须使用国内主流服务。
- 第一版采用 API Key 直连，不走自建中转服务。
- 第一版不使用多模型生产架构。
- 第一版不使用 Coding Plan key。
- 模型必须支持稳定的结构化输出。
- 模型选择必须可配置，默认推荐千问，但不能在代码中写死真实密钥。

### 10.2 业务约束

- 自动通过必须极度保守。
- 人工审核仍是正式流程的一部分。
- 系统要尽量减少“明显不对的候选进入审核列表”的情况。

### 10.3 运行约束

- 运行环境以 Windows 本地为主。
- 模型调用阶段要求网络可用。
- 目标电脑只要求能稳定访问一个模型服务提供方。
- 第一版允许内部受控环境直接保存和使用 API Key。

## 11. MVP 范围

- 本地候选召回

## 12. 验收标准草案

- 验收标准 1：
  使用有效的百炼 API Key，系统可完成“上传 -> 字段对照 -> 标准化 -> 候选召回 -> 模型裁决 -> Excel 导出”全流程。
- 验收标准 2：
  每条客户商品都必须得到一个明确的 `match_status`，且输出结构化说明。
- 验收标准 3：
  `auto_matched` 结果必须带有明确置信度和原因说明。
- 验收标准 4：
  `manual_review` 与 `unmatched` 结果不得伪装成已确认匹配。
- 验收标准 5：
  审核人员能看到推荐候选与备选候选摘要，而不是只看到一个模糊结果。
- 验收标准 6：
  在一组人工标注验证样本上，`auto_matched` 的精度目标应达到 98% 以上。
- 验收标准 7：
  在同一组验证样本上，`suggested + manual_review` 的 Top3 候选命中目标应达到 85% 以上。
- 验收标准 8：
  在仅能访问单一模型服务的目标电脑上，系统仍可完成完整生产链路。
- 验收标准 9：
  当模型调用失败、超时或结构化输出异常时，系统必须给出显式错误，不允许静默写入错误匹配结果。

## 13. 假设

- 假设 1：
  第一版优先服务内部或受控客户环境，允许通过 API Key 直连模型。
- 假设 2：
  默认推荐的 `qwen-plus` 可以同时承担标准化与裁决任务。
- 假设 3：
  我司商品库规模在第一版本地候选召回可接受的范围内。
- 假设 4：
  第一版不接向量召回，而是通过标准化结果和本地候选缩圈完成召回。
- 假设 5：
  第一版不做模型微调，而是通过任务拆分、提示词和分级策略完成效果控制。

## 14. 当前仍需在实施阶段细化但不阻塞开工的问题

- 本地候选召回采用何种索引与打分方式更稳。
- 第一版导出文件中是否展示完整 Top3 候选明细，还是只展示候选摘要。
- 本地 API Key 存储是否先用环境变量或本地配置文件，还是第一版就接系统密钥库。
- 审核结果回流是先写 Excel，还是同步写本地数据库。
