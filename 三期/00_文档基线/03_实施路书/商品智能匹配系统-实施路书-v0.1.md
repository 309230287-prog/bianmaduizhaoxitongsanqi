# 商品智能匹配系统实施路书

- 版本：v0.1
- 日期：2026-03-24
- 状态：待确认
- 对应需求：商品智能匹配系统-需求文档-v0.1.md

## Objective

- Target outcome:
  - 交付一个可在 Windows 电脑本地安装运行的商品智能匹配客户端 MVP。
  - 用户可上传“我司商品库”和“客户商品库”两份 Excel。
  - 用户可通过字段对照表完成列映射。
  - 系统可执行名称优先的商品匹配，并将结果回写到客户 Excel 后侧。
  - 系统可导出带颜色标识的新 Excel 结果文件。
  - AI 为可选增强能力，不作为基础运行前提。
- Source requirements:
  - D:\编码对照项目\docs\requirements\商品智能匹配系统-需求文档-v0.1.md
- Preconditions:
  - 需求文档方向已确认。
  - 已有两份真实 Excel 可用于样例验证。
  - 当前环境已具备 Python、Excel 处理、OCR/PDF、GitHub CLI 等基础能力。

## Recommended MVP Architecture

- Desktop shell:
  - 推荐采用“本地 Web 界面 + Windows 桌面壳”的方式。
  - 建议 MVP 技术组合：Python + FastAPI + Jinja/HTML + SQLite + 本地桌面壳打包。
- Matching engine:
  - 规则优先，AI 增强，人工兜底。
  - 名称优先识别商品主词，再做品牌、规格、单位、分类判断。
- Storage:
  - SQLite 保存字段映射模板、历史匹配关系、人工审核记录、别名映射。
- Export:
  - 使用 openpyxl / pandas 在客户原始表后追加匹配结果列并导出新文件。
- AI integration:
  - 设置页提供 API Base URL、API Key、模型名、启用开关。

## Milestones

- Milestone 1:
  - 数据契约明确，字段对照流程跑通，形成可执行样例。
- Milestone 2:
  - 规则匹配 MVP 跑通，可生成结果 Excel。
- Milestone 3:
  - Windows 客户端 MVP 可安装、可运行、可导出。
- Milestone 4:
  - 使用真实 Excel 做一轮业务验收并修正规则。

## Phase Plan

### Phase 0 - 技术基线与样例锁定

- Goal:
  - 锁定 MVP 技术路线和第一批真实验证样本。
- Why this phase exists:
  - 如果技术壳和样本不先锁定，后续匹配和界面开发很容易返工。
- Inputs required:
  - 已确认的需求文档
  - 当前两份真实 Excel
- Tasks:
  - 确认 MVP 技术架构：Python 本地服务 + 本地桌面壳 + SQLite
  - 固定第一批样例文件和 sheet 使用范围
  - 明确结果文件命名规则和存放规则
  - 明确历史匹配关系、别名映射、字段模板的本地存储方案
- Deliverables:
  - 技术选型说明
  - 样例文件清单
  - 本地数据存储清单
- Validation gate:
  - 形成一页“架构与样例冻结说明”，后续阶段按此执行
- Risks:
  - 如果后续改成别的桌面技术壳，会导致 UI 与打包方案返工
- Rollback or fallback:
  - 若桌面壳方案不稳定，可暂时退回“本地浏览器访问 FastAPI 页面”的开发模式，不阻塞核心业务逻辑实现

### Phase 1 - 字段对照与导入流程

- Goal:
  - 跑通双 Excel 上传和字段对照表流程。
- Why this phase exists:
  - 字段映射是整个系统的入口，不先跑通，后续匹配逻辑没有稳定输入。
- Inputs required:
  - 两份真实 Excel
  - 标准字段定义：商品编码、商品名称、规格、品牌、单位、分类
- Tasks:
  - 实现 Excel 导入与表头读取
  - 实现双表字段对照表 UI
  - 增加字段必填校验与缺失提示
  - 支持保存和复用字段映射模板
- Deliverables:
  - 双 Excel 导入页
  - 字段对照配置页
  - 字段模板存储结构
- Validation gate:
  - 使用真实 Excel 能成功完成字段对照并保存配置
- Risks:
  - 真实数据 sheet 结构可能不稳定
  - 同一列名可能重复或空列较多
- Rollback or fallback:
  - 先只支持单个 sheet 和手工字段选择，不做自动猜字段

### Phase 2 - 数据标准化与候选召回

- Goal:
  - 把输入数据转成可比对的标准化结构，并缩小匹配候选范围。
- Why this phase exists:
  - 没有标准化，后面的匹配容易把“写法不同但同物”与“写法相近但不同物”混在一起。
- Inputs required:
  - 字段映射结果
  - 真实样例数据
- Tasks:
  - 名称清洗：空格、标点、大小写、噪音词
  - 品牌标准化：品牌别名、中英文映射
  - 规格标准化：提取数值和单位
  - 单位标准化：件/个/只、台/部、kg/g、斤/kg 等映射
  - 分类标准化：统一类目文本
  - 建立候选召回逻辑：按名称主词、分类、品牌召回 Top N
- Deliverables:
  - 标准化模块
  - 候选召回模块
  - 初版别名/单位映射表
- Validation gate:
  - 用样例数据抽查 20-50 条，确认名称、品牌、规格、单位拆解结果可读可解释
- Risks:
  - 品牌列不稳定或缺失
  - 规格写法极不统一
  - 包装层级和销售单位混在同一字段
- Rollback or fallback:
  - 若规格解析难度过高，第一版先保证核心数值和单位识别，不追求全覆盖复杂包装描述

### Phase 3 - 规则匹配引擎 MVP

- Goal:
  - 实现“规则优先”的基础匹配引擎。
- Why this phase exists:
  - 第一版必须先有稳定、可解释、可控的规则结果，AI 只能在此基础上增强。
- Inputs required:
  - 标准化结构
  - 候选召回结果
  - 历史匹配表结构
- Tasks:
  - 实现历史命中优先逻辑
  - 实现名称优先判断逻辑
  - 实现品牌、规格、单位、分类校验逻辑
  - 实现结果分级：历史命中、自动匹配、建议匹配、未匹配、数据不足
  - 记录匹配说明，支持人工追溯原因
- Deliverables:
  - MVP 匹配引擎
  - 结果分级规则
  - 匹配解释字段
- Validation gate:
  - 选取真实样例进行人工抽查，确认结果解释基本符合业务常识
- Risks:
  - 自动匹配阈值过松导致错配
  - 规则过严导致建议匹配过多
- Rollback or fallback:
  - 第一版宁可保守，多给建议匹配，也不要过度自动确认

### Phase 4 - 结果回写、审核与导出

- Goal:
  - 让业务人员能直接拿到可用结果文件。
- Why this phase exists:
  - 这是业务价值最直观的阶段，没有结果回写和导出，系统就还不是可交付工具。
- Inputs required:
  - 匹配结果数据结构
- Tasks:
  - 在客户原始表后追加我司匹配结果列
  - 增加颜色标识：绿色、黄色、红色、灰色
  - 增加审核状态和审核备注字段
  - 生成新的导出文件，不覆盖原文件
- Deliverables:
  - 结果回写模块
  - Excel 导出模块
  - 导出命名规则
- Validation gate:
  - 真实 Excel 可成功导出，且业务人员能一眼看出匹配状态
- Risks:
  - Excel 样式兼容性问题
  - 超大文件导出性能不稳定
- Rollback or fallback:
  - 如果复杂样式导致不稳定，第一版先保证颜色填充和基础列回写，不做复杂格式美化

### Phase 5 - Windows 客户端壳与设置页

- Goal:
  - 将本地能力封装为可直接使用的 Windows 客户端。
- Why this phase exists:
  - 需求明确要求像 Windows 软件一样安装和使用。
- Inputs required:
  - 前面已跑通的本地功能
- Tasks:
  - 搭建桌面启动壳
  - 整合本地 Web 界面或等效前端界面
  - 增加设置页：API Base URL、API Key、模型名、AI 开关
  - 增加本地数据目录和日志目录规范
  - 增加安装包打包方案
- Deliverables:
  - 可启动的 Windows 客户端 MVP
  - 设置页
  - 初版安装包或可运行发布包
- Validation gate:
  - 在一台新的 Windows 机器或干净环境上可以打开、导入、匹配、导出
- Risks:
  - 桌面壳与本地服务集成不稳定
  - 打包后路径和权限问题
- Rollback or fallback:
  - 若安装包阶段不稳定，可先交付免安装运行包，再迭代安装器

### Phase 6 - AI 增强与业务验收

- Goal:
  - 在规则基础上引入 AI 提升模糊匹配效果，并完成真实业务验收。
- Why this phase exists:
  - AI 是增强项，应在规则 MVP 稳定后再接入，避免把核心正确性绑在外部模型上。
- Inputs required:
  - 规则匹配 MVP
  - 可用 API 配置
  - 人工审核样本集
- Tasks:
  - 接入 AI 名称理解与候选排序能力
  - 让 AI 仅处理模糊候选，不直接全库自由匹配
  - 比较“纯规则”与“规则+AI”的效果差异
  - 用真实业务样本做一轮验收
  - 调整阈值和结果分级策略
- Deliverables:
  - AI 辅助匹配模块
  - 业务验收记录
  - 阈值调整建议
- Validation gate:
  - AI 增强后，建议匹配质量有明显改善，且没有显著提高错配风险
- Risks:
  - AI 输出不稳定
  - 外部 API 成本和时延不可控
  - 业务方误把 AI 结果当绝对正确
- Rollback or fallback:
  - AI 模块必须可关闭；关闭后系统仍能完整运行规则匹配流程

## Execution Rules Summary

为避免实施路书本身变成规则细则全集，完整匹配规则和执行规格单独维护在配套文档中。
本路书只保留与实施顺序直接相关的执行概要。

实施概要如下：
- Phase 1 之后，程序所有输入都必须先转成统一标准字段结构
- Phase 2 重点不是直接匹配，而是先完成名称清洗、规格提取、单位识别、品牌识别、商品名称提取
- Phase 3 必须建立“候选召回 -> 规则比对 -> 结果分级”的稳定链路
- 品牌、规格、单位、分类冲突规则必须先落成程序硬边界，再考虑 AI 增强
- AI 只能作为模糊候选增强，不得越过硬冲突规则
- 历史匹配关系、品牌词库、单位映射、规格归一规则需要作为持续资产沉淀
- 商品库持续更新时，应支持重新标准化和重新匹配，而不是一次性人工整理

## Dependencies

- Dependency 1:
  - 需求文档冻结，不再频繁改核心流程
- Dependency 2:
  - 样例 Excel 在开发期保持可用
- Dependency 3:
  - MVP 技术壳尽早定稿，避免 UI 和打包路线反复切换
- Dependency 4:
  - 历史匹配表、别名表、字段模板表需要统一 SQLite 结构

## Risks and Unknowns

- Risk 1:
  - 真实 Excel 中品牌和规格字段可能长期不稳定，导致规则设计需支持降级
- Risk 2:
  - 商品名称中品牌、规格、包装信息混写，标准化难度高于文档描述
- Risk 3:
  - 自动匹配阈值若定得过激进，会带来高成本错配风险
- Risk 4:
  - Windows 桌面打包方案若选择不当，会增加大量非业务开发成本
- Risk 5:
  - AI 若过早介入核心判断，可能让系统失去可解释性和可控性

## Approval Gates

- Gate 1:
  - 确认 MVP 技术壳：本地 Web + 桌面壳路线是否采用
- Gate 2:
  - 确认 Phase 2 输出的数据标准化方案是否符合业务认知
- Gate 3:
  - 确认 Phase 3 的结果分级规则是否符合实际审核习惯
- Gate 4:
  - 确认 Phase 5 的 Windows 客户端交付形态：安装包还是免安装运行包
- Gate 5:
  - 确认是否在 MVP 阶段就启用 AI 增强，还是先纯规则上线试运行

## Recommended Next Step

- First execution slice:
  - 先完成 Phase 0 和 Phase 1，也就是“技术壳冻结 + 双 Excel 上传与字段对照流程跑通”。
- Why this slice comes first:
  - 因为字段对照是整条链路的入口，只有输入稳定，后面的标准化、匹配和导出才不会反复返工。
