# 商品智能匹配系统 - 实施路书

- 版本：v0.3
- 日期：2026-03-28
- 状态：待执行
- 对应需求：`docs/requirements/商品智能匹配系统-需求文档-v0.3.md`

## Objective

- Target outcome：
  交付一个基于单模型生产主链路的商品匹配 MVP，运行在 Windows 本地环境中，能够通过“默认推荐千问模型的标准化 + 本地候选召回 + 默认推荐千问模型的单模型裁决”完成客户商品库与我司商品库的对照，并以“少错配”为第一目标输出结果。
- Source requirements：
  `docs/requirements/商品智能匹配系统-需求文档-v0.3.md`
- Preconditions：
  - 新版需求边界已确认
  - 百炼普通 API Key 可用
  - 当前 MVP 的上传、字段映射、导出骨架已存在
  - 有一批真实样本可用于评测与验收

## Milestones

- Milestone 1：
  冻结单模型数据契约、评测样本与验收口径。
- Milestone 2：
  跑通默认推荐生产模型的标准化与本地候选召回链路。
- Milestone 3：
  跑通默认推荐生产模型的单模型裁决、分级输出和审核导出。
- Milestone 4：
  用真实数据完成效果验收，并决定是否需要向量或第二模型作为后续增强。

## Phase Plan

### Phase 0 - 需求冻结与评测样本准备

- Goal：
  把“少错配优先”的业务目标、分级口径和评测样本固定下来。
- Why this phase exists：
  如果没有统一评测口径，后面很容易陷入“感觉模型更聪明”，而不是“结果可验收”。
- Inputs required：
  - 已确认的 v0.3 需求文档
  - 真实业务 Excel
  - 过往匹配结果样本
- Tasks：
  - 冻结四级结果状态定义
  - 定义人工标注评测样本集，建议 200 到 500 条
  - 明确 `auto_matched` 精度目标与 Top3 候选命中目标
  - 冻结“第一版生产主链路只使用一个模型服务”的边界
- Deliverables：
  - 评测样本清单
  - 评测指标说明
  - 结果分级口径说明
- Validation gate：
  项目组可以用同一份样本和同一套口径判断“这次改动到底有没有进步”。
- Risks：
  - 没有统一标注口径会导致后续验收失真
  - 样本集偏科会让效果判断失真
- Rollback or fallback：
  若短期无法凑齐完整样本，先做一版最小评测集，但不得跳过评测定义直接编码。

### Phase 1 - 单模型提供方与配置层落地

- Goal：
  建立可配置、可追踪、但足够收敛的单模型调用基础层。
- Why this phase exists：
  这次方案收敛的核心，就是把生产依赖压到一条外部模型链路上，先确保它稳定。
- Inputs required：
  - 百炼 API 接入信息
  - 当前本地运行骨架
- Tasks：
  - 设计 Provider 配置结构，只保留单模型所需字段
  - 设计统一的模型调用入口，用于标准化和裁决两类任务
  - 设计模型选择配置项，默认推荐百炼 `qwen-plus`
  - 设计超时、重试、限流、错误日志策略
  - 设计本地 API Key 配置存储方案
  - 明确 API Key 读取方式，不允许把真实密钥写进源码或仓库
  - 明确配置页字段与默认值
- Deliverables：
  - 单模型 Provider 配置契约
  - 通用模型调用契约
  - 模型配置项说明
  - 错误与日志策略说明
- Validation gate：
  不写业务逻辑的前提下，能够清楚说明“系统如何在两个任务里复用同一个模型服务”。
- Risks：
  - 结构化输出稳定性不如预期
  - 直连 API Key 带来的密钥管理风险
- Rollback or fallback：
  若本地密钥管理暂时做不完整，第一版先保证配置清晰和错误可见，后续再补更安全的存储方案。

### Phase 2 - 单模型标准化链路落地

- Goal：
  用默认推荐的千问生产模型建立稳定的商品标准化链路。
- Why this phase exists：
  如果标准化层不稳定，后面的候选召回和裁决都会被拖垮。
- Inputs required：
  - 字段映射结果
  - 标准化 JSON schema
  - 评测样本
- Tasks：
  - 定义标准化输出结构
  - 设计标准化 prompt 与结构化输出 schema
  - 明确原始字段与标准化字段如何并存
  - 定义标准化缓存策略
  - 设计标准化失败时的错误呈现方式
- Deliverables：
  - 标准化字段契约
  - 标准化 prompt 草案
  - 标准化缓存方案
- Validation gate：
  抽查样本时，品牌、商品主词、规格、单位、分类的抽取结果可读、可解释、可复核。
- Risks：
  - 模型会把口语、品牌、商品名互相识别错位
  - 规格和包装层级抽取不稳定
- Rollback or fallback：
  如果一次性输出全部字段不稳定，可拆成两次调用实验，但正式生产链路仍保持单模型服务不变。

### Phase 3 - 本地候选召回链路落地

- Goal：
  构建“先本地缩小候选，再让模型裁决”的稳定候选链路。
- Why this phase exists：
  单模型方案要成立，关键不是让模型看全库，而是先把全库变成一小组可判断候选。
- Inputs required：
  - 标准化后的我司商品库
  - 标准化后的客户商品库
  - 评测样本
- Tasks：
  - 设计候选召回文本拼装策略
  - 设计本地商品索引或检索结构
  - 设计逐条召回 Top-N 策略
  - 设计召回结果记录结构
  - 定义召回失败与重试行为
- Deliverables：
  - 本地召回方案
  - Top-N 候选策略
  - 召回评测方法
- Validation gate：
  在评测样本上，正确答案进入 Top-N 的命中率达到可接受水平，并能稳定复现。
- Risks：
  - 本地召回做得不够好，会直接限制后续裁决效果
  - 召回范围过大时，裁决成本和时延会上升
- Rollback or fallback：
  若 Top20 成本过高，可先用 Top10 验证；若召回明显不足，再扩回 Top20。

### Phase 4 - 单模型裁决与分级链路落地

- Goal：
  形成“同一个模型既做理解又做最终裁决”的稳定判断机制。
- Why this phase exists：
  这是整条单模型生产链路里最直接决定错配率的环节。
- Inputs required：
  - 候选召回结果
  - 裁决 JSON schema
  - 四级状态定义
- Tasks：
  - 定义单模型裁决 prompt
  - 定义裁决输出 JSON
  - 定义裁决结果到四级状态的映射
  - 定义低置信度与高风险样本的处理逻辑
  - 定义 `auto_matched` 的保守放行条件
- Deliverables：
  - 单模型裁决契约
  - 四级状态映射表
  - 风险标记说明
- Validation gate：
  对同一批样本重复测试时，裁决输出结构稳定，且 `auto_matched` 精度满足目标。
- Risks：
  - 单模型如果输出过于激进，会直接放大错配风险
  - JSON 输出偶发不稳定时，会影响整批处理可靠性
- Rollback or fallback：
  若 `auto_matched` 精度不达标，先收紧放行阈值，把更多结果归入 `suggested` 或 `manual_review`。

### Phase 5 - 审核体验、结果导出与回流准备

- Goal：
  让审核人员真正看到“更少错误、更好解释”的结果，并为后续回流积累基础。
- Why this phase exists：
  用户的核心诉求不是模型多高级，而是审核时别再看到大量明显错误候选。
- Inputs required：
  - 裁决结果
  - 备选候选摘要结构
  - 现有导出逻辑
- Tasks：
  - 设计审核结果展示字段
  - 设计导出 Excel 的新增列
  - 设计 `suggested` 与 `manual_review` 的候选摘要呈现方式
  - 设计错误、超时、结构化输出异常的提示方式
  - 设计审核结果的基础回流结构
- Deliverables：
  - 新版审核展示结构
  - 新版导出字段结构
  - 回流字段草案
- Validation gate：
  审核人员可以快速看到推荐候选、备选候选、置信度和原因，而不是只看到一个模糊结论。
- Risks：
  - 导出信息过多导致 Excel 难读
  - 审核页面信息密度过高反而降低效率
- Rollback or fallback：
  第一版先保证“主候选 + 候选摘要 + 置信度 + 原因”四类关键信息，避免一次性塞入过多字段。

### Phase 6 - 真实数据验收与下一阶段分叉

- Goal：
  用真实数据验证这次转型是否真的降低了错配风险，并决定后续是否需要向量或第二模型增强。
- Why this phase exists：
  单模型方案要先在真实业务里站住脚，后续增强才有意义。
- Inputs required：
  - 评测样本
  - 全链路运行结果
  - 业务抽检反馈
- Tasks：
  - 对比旧版规则路线与新版单模型路线
  - 抽查 `auto_matched` 精度
  - 统计 `suggested/manual_review` 的 Top3 候选命中情况
  - 调整 prompt、Top-N 和分级阈值
  - 决定下一阶段是否引入向量召回或 challenger 模型做实验
- Deliverables：
  - 验收报告
  - 上线参数建议
  - 后续迭代清单
- Validation gate：
  达到需求文档中的验收标准草案，尤其是自动通过精度与审核候选质量目标。
- Risks：
  - 单模型效果提升不及预期
  - 本地召回效果不足时，可能需要引入下一阶段增强
- Rollback or fallback：
  若新版在验收集上未显著优于旧版，不默认替换旧链路，而是以灰度或实验模式继续迭代。

## Dependencies

- Dependency 1：
  百炼普通 API Key 可稳定使用。
- Dependency 2：
  目标机器具备可访问百炼 API 的网络条件。
- Dependency 3：
  有一批可人工标注或已知答案的真实样本用于验收。
- Dependency 4：
  当前上传、字段映射、导出骨架继续保留，不另起炉灶重做 UI。

## Risks and Unknowns

- Risk 1：
  标准化模型把品牌、商品名、规格拆错位，会连锁影响本地召回和裁决。
- Risk 2：
  本地候选召回做得不好，会让后面再强的裁决也无用武之地。
- Risk 3：
  单模型如果偏激进，会直接放大错配风险。
- Risk 4：
  本地直连 API Key 虽然适合 MVP，但长期仍存在安全与运维风险。
- Risk 5：
  如果没有真实评测集，这次架构转型可能缺少客观验收基线。

## Approval Gates

- Gate 1：
  确认 v0.3 需求文档冻结，可以正式按单模型主链路进入实施。
- Gate 2：
  确认第一版默认推荐 `qwen-plus`，但生产模型为配置项，不在代码中写死。
- Gate 3：
  确认评测样本集与验收指标。
- Gate 4：
  确认第一版允许客户端 API Key 直连方式。
- Gate 5：
  确认真实数据验收通过后，是否进入“向量增强”或“challenger 模型实验”阶段。

## Recommended Next Step

- First execution slice：
  先完成 Phase 0 和 Phase 1，也就是“冻结评测口径 + 冻结单模型调用与配置契约”。
- Why this slice comes first：
  因为这次转型的风险不在代码细节，而在目标与边界是否稳定。只有先把评测口径和单模型契约冻住，后面的标准化、召回和裁决实现才不会反复返工。
