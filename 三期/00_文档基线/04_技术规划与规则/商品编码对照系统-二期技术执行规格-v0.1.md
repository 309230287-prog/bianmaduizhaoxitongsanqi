# 商品编码对照系统 - 二期技术执行规格

- 版本：v0.1
- 日期：2026-04-18
- 状态：技术参数草案
- 对应需求：`docs/requirements/商品编码对照系统-需求文档-二期语义翻译-v0.1.md`
- 对应路书：`docs/route-map/商品编码对照系统-二期语义翻译实施路书-v0.1.md`
- 核心原则：大模型负责理解和判断，程序负责流程和留痕

## 1. 文档目的

这份文档补充二期的技术参数、指标和框架建议。

它解决的问题是：

- 二期用什么技术框架落地
- 大模型怎么调用
- 输入输出结构怎么定
- 候选池怎么控制
- 批处理、速度、成本怎么估算
- 自动落码和人工审核的技术指标怎么验收
- 哪些指标达不到就不能产品化

这份文档不是最终代码设计。

它是进入样本验证和原型开发前的技术执行规格。

## 2. 总体技术路线

二期建议采用：

**本地 Web 工具 + 大模型语义翻译服务 + 本地持久化数据 + Excel 导入导出。**

推荐形态：

```text
浏览器页面
-> 本地后端服务
-> Excel 解析层
-> 数据整理层
-> 候选池生成层
-> 大模型语义翻译层
-> 证据对齐与结果分级层
-> 人工审核与历史关系层
-> 产品记忆系统
-> Excel 导出层
```

大模型是主力理解层。

程序系统不负责最终语义拍板，只负责把上下文组织好、把结果保存好、把风险暴露出来。

## 3. 推荐技术栈

### 3.1 后端

推荐：

- Python 3.11+
- FastAPI
- Pydantic
- openpyxl
- SQLite
- httpx
- Jinja2 或轻量前端框架

原因：

- Python 适合处理 Excel 和数据清洗
- FastAPI 适合本地 Web 服务和 API 化
- Pydantic 适合约束大模型 JSON 输出
- SQLite 足够支撑本地样本、任务、审核和历史关系
- openpyxl 已能稳定处理 `.xlsx`

### 3.2 前端

二期原型阶段建议先保持简单。

可选：

- FastAPI + Jinja2 服务端模板
- 或 Vite + React

当前建议：

**先用 Jinja2 或轻量页面跑通原型，不急着做复杂前端。**

理由：

- 二期关键风险在语义翻译，不在 UI
- 样本验证阶段需要快
- 页面只需满足导入、查看、审核、导出

如果进入正式产品化，再考虑更完整前端。

### 3.3 数据存储

推荐 SQLite。

建议存储：

- 导入任务
- 客户原始记录
- 我司商品快照
- 候选池
- 大模型输入
- 大模型输出
- 结果分级
- 人工审核结果
- 历史确认关系
- 业务等价关系
- 客户表达习惯
- 商品语义别名
- 失败案例
- 模型纠错记录
- 运行日志

### 3.4 大模型接口

大模型接口必须支持：

- 中文语义理解
- 长上下文
- JSON 结构化输出
- 较稳定的指令遵循
- 可配置模型提供方、模型名、Base URL、API Key

模型提供方暂不在技术规格中定死。

但第一阶段测试时，建议选择一个中文能力稳定、成本可控、接口兼容 OpenAI 风格的大模型。

## 4. 模块边界

### 4.1 Excel 导入模块

职责：

- 读取 `.xlsx`
- 读取工作表
- 读取表头
- 读取样例行
- 处理重复列名
- 保留原始单元格值

不负责：

- 商品语义判断
- 自动清洗掉不理解的内容

### 4.2 字段映射模块

职责：

- 帮用户把客户库字段映射到标准字段
- 帮用户把我司库字段映射到标准字段
- 支持模板保存
- 支持缺字段提示

不负责：

- 把字段映射当成商品语义理解

### 4.3 数据整理模块

职责：

- 把一行客户记录整理成模型输入格式
- 把我司候选整理成模型输入格式
- 保留原始字段和值
- 标明字段来源

不负责：

- 擅自删除不理解的信息
- 擅自脑补缺失字段

### 4.4 候选池模块

职责：

- 从我司商品库中筛出一批候选
- 尽量避免漏掉语义等价候选
- 保留候选来源和筛选理由

不负责：

- 最终判断是否同商品
- 单独决定自动落码

### 4.5 大模型语义翻译模块

职责：

- 理解客户记录
- 理解我司候选
- 做证据对齐
- 识别风险
- 输出结构化 JSON
- 给出业务可读解释

这是二期核心模块。

### 4.6 结果分级模块

职责：

- 校验大模型输出
- 根据风险和状态转换为系统状态
- 防止模型输出越权状态
- 保留模型原始判断和系统最终状态

### 4.7 人工审核模块

职责：

- 展示客户记录、候选、证据、风险
- 允许确认、改选、标记无匹配
- 允许记录审核备注
- 允许沉淀历史关系

### 4.8 导出模块

职责：

- 基于客户原始 Excel 生成新文件
- 追加系统结果列
- 不覆盖原始文件

### 4.9 产品记忆系统

职责：

- 保存人工确认过的客户表达和我司商品关系
- 保存业务等价关系
- 保存客户常见写法和表达习惯
- 保存商品语义别名和系列词解释
- 保存模型曾经出错的案例
- 在后续判断中为候选池和大模型提示提供上下文

产品记忆系统不是开发过程记忆。

它是产品能力的一部分。

目标是让系统越用越顺、越用越聪明。

## 4.10 记忆系统分层设计

二期应设计独立的产品记忆系统。

建议分为五层。

### 4.10.1 任务记忆

任务记忆记录单次导入和处理过程。

主要用于断点续跑、排错和复盘。

建议记录：

- 任务 ID
- 文件名
- 导入时间
- 字段映射
- 处理进度
- 模型调用次数
- 错误记录
- 导出文件

任务记忆通常只影响当前批次。

### 4.10.2 人工确认记忆

人工确认记忆记录人工审核后的确定关系。

这是最重要的长期记忆。

建议记录：

- 客户原始表达
- 客户字段快照
- 客户名称
- 客户规格
- 客户单位
- 客户备注
- 我司商品编码
- 我司商品名称
- 确认人
- 确认时间
- 确认理由
- 适用条件
- 是否允许用于弱自动落码
- 是否需要复核

人工确认记忆可以影响：

- 候选池排序
- 大模型上下文
- 弱自动落码
- 人工审核提示

但不能无条件覆盖当前证据。

如果当前记录的规格、单位、品牌、包装或备注发生关键变化，必须重新审核。

### 4.10.3 客户表达习惯记忆

客户表达习惯记忆记录某个客户常用的写法。

例如：

- 该客户常把 `听装` 写成 `罐`
- 该客户常把 `件` 当作整箱单位
- 该客户常把规格写在商品名称里
- 该客户某些编号不稳定，不能作为强依据

建议记录：

- 客户标识
- 表达类型
- 原始表达
- 解释后的含义
- 适用品类
- 可信等级
- 来源记录
- 最近验证时间

客户表达习惯记忆主要影响：

- 字段理解
- 候选池生成
- Prompt 中的客户上下文

### 4.10.4 商品语义记忆

商品语义记忆记录商品层面的通用知识。

例如：

- `番茄` 和 `西红柿` 可等价
- `金标` 在某些调味品中是系列或等级标识，不是品牌
- `听装` 和 `罐装` 在某些饮料场景可等价
- `1*12*500ml` 不应直接压成 `500ml`

建议记录：

- 语义词
- 语义类型
- 等价词
- 适用品类
- 不适用场景
- 风险说明
- 来源
- 审核状态

商品语义记忆主要影响：

- 大模型提示
- 候选池扩展
- 风险判断
- 弱自动落码条件

### 4.10.5 失败案例记忆

失败案例记忆记录系统曾经犯错或差点犯错的场景。

这是防止系统重复犯错的关键。

建议记录：

- 原客户记录
- 模型原判断
- 人工纠正结果
- 错误类型
- 错误原因
- 应新增的风险提示
- 是否需要调整 Prompt
- 是否需要调整候选池

失败案例记忆主要影响：

- 风险提示
- Prompt 禁止规则
- 测试样本扩充
- 自动落码收紧

## 4.11 记忆系统使用原则

记忆系统必须遵守：

- 记忆只能增强判断，不能替代证据。
- 记忆命中不等于自动落码。
- 历史关系必须检查适用条件。
- 失败案例优先级高于自动化率。
- 所有可用于弱自动落码的记忆必须有人工确认来源。
- 模型自己生成的猜测不能直接进入长期记忆。
- 长期记忆需要可查看、可禁用、可修正。

大白话说：

**记忆是经验，不是圣旨。**

它可以让系统更顺，但不能让系统跳过当前证据。

## 5.8 记忆命中流程

每条客户记录处理时，建议按以下顺序使用记忆：

```text
客户原始记录
-> 查询人工确认记忆
-> 查询客户表达习惯记忆
-> 查询商品语义记忆
-> 查询业务等价关系
-> 查询失败案例记忆
-> 生成候选池
-> 组装大模型上下文
-> 大模型判断
-> 系统结果分级
-> 人工审核
-> 写入或更新记忆
```

记忆对系统的作用分三类：

- 进入候选池：帮助找到可能候选
- 进入 Prompt：帮助大模型理解上下文
- 进入结果分级：支持弱自动落码或触发人工审核

注意：

失败案例记忆应优先用于收紧自动落码。

人工确认记忆可以支持弱自动落码。

客户表达习惯记忆和商品语义记忆通常只作为理解辅助，不应单独决定落码。

## 6. 大模型调用策略

### 6.1 调用阶段

二期建议先采用两段式调用验证。

第一段：客户记录语义理解。

目标：

- 识别客户记录表达的商品身份
- 找出关键身份信号
- 找出强约束、弱约束、不确定信息

第二段：候选证据对齐与裁决。

目标：

- 对齐客户记录和候选商品
- 判断同一业务身份
- 给出结果分级和风险

如果后续验证发现一次调用稳定，也可以合并。

但第一阶段不建议直接合并，以免难以排查模型到底错在理解还是裁决。

### 6.2 Prompt 原则

Prompt 必须明确：

- 不允许脑补客户未表达的信息
- 不允许只按名称相似判断
- 不允许忽略规格、包装、单位、备注
- 不允许把不确定结果强行自动落码
- 必须解释证据和风险
- 必须输出 JSON

### 6.3 温度参数

建议：

- `temperature`: 0 到 0.2
- `top_p`: 0.8 到 1.0

理由：

商品编码对照不是创作任务。

输出应稳定、保守、可复现。

### 6.4 超时和重试

建议：

- 单次请求超时：60 秒
- 最大重试次数：2 次
- 重试仅用于网络错误、限流、JSON 格式错误
- 不因模型判断不满意而自动重试

### 6.5 并发

验证阶段建议：

- 并发数：1 到 3

产品原型阶段建议：

- 默认并发数：3
- 最大并发数：5

原因：

- 避免接口限流
- 避免成本失控
- 方便排查模型输出

### 6.6 上下文大小

建议单次候选数：

- 黄金样本验证：5 到 10 个候选
- 原型阶段默认：10 个候选
- 困难样本上限：20 个候选

原则：

- 候选太少容易漏正确答案
- 候选太多会增加模型成本、上下文噪音和判断不稳定

## 7. 候选池技术参数

### 7.1 候选池目标

候选池目标不是找字面最像。

候选池目标是：

**尽量保留可能表达同一业务商品身份的我司商品。**

### 7.2 候选来源

候选来源建议包括：

- 名称包含
- 品名关键词
- 品牌关键词
- 规格关键词
- 单位关键词
- 类别辅助
- 同义词词表
- 历史确认关系
- 业务等价关系
- 大模型生成的检索关键词

### 7.3 候选池数量

建议参数：

- 最小候选数：3
- 默认候选数：10
- 最大候选数：20

如果候选数为 0，应进入未匹配或人工审核，不应让模型凭空猜。

### 7.4 候选池覆盖率指标

黄金样本阶段：

- Top10 覆盖率目标：不低于 90%
- Top20 覆盖率目标：不低于 95%

困难样本阶段：

- Top20 覆盖率目标：不低于 85%

说明：

这里的覆盖率指人工确认正确商品进入候选池。

如果正确商品没有进入候选池，后续大模型再强也无法选对。

### 7.5 候选池失败处理

如果候选池没有正确答案，应记录：

- 客户记录
- 正确商品
- 为什么没召回
- 缺少哪个关键词或语义关系
- 是否需要补充同义词或业务等价关系

## 8. 结果分级技术规则

### 8.1 状态枚举

系统状态建议使用：

- `strong_auto_code`
- `weak_auto_code`
- `suggested_code`
- `manual_review`
- `unmatched`
- `model_error`

### 8.2 强自动落码

允许条件：

- 核心品名一致或业务等价
- 强约束无冲突
- 规格和包装层级无关键差异
- 单位无关键差异
- 不需要脑补
- 候选唯一或第一候选优势明显
- 模型解释证据完整

禁止条件：

- 存在品牌冲突
- 存在规格冲突
- 存在包装层级冲突
- 备注可能改变身份
- 模型需要补充客户未写信息
- 多个候选都能完整解释客户记录

### 8.3 弱自动落码

允许条件：

- 差异只是表达差异
- 有业务等价关系或历史确认关系支撑
- 不影响商品身份、价格、单位、包装或结算
- 必须留痕

### 8.4 建议落码

适用：

- 第一候选明显更强
- 但仍有轻微不确定
- 需要人工快速确认或抽查

### 8.5 必须人工审核

触发条件：

- `brand_conflict`
- `spec_conflict`
- `package_conflict`
- `unit_conflict`
- `series_or_grade_conflict`
- `remark_changes_identity`
- `needs_unstated_assumption`
- `multiple_valid_candidates`
- `insufficient_customer_info`

### 8.6 未匹配

适用：

- 候选池为空
- 候选均有核心冲突
- 客户信息不足且无法判断
- 模型明确判断无可靠候选

## 9. 质量指标

### 9.1 黄金样本阶段指标

建议先做 30 条黄金样本。

通过标准：

- JSON 输出有效率：100%
- 核心品名理解准确率：不低于 95%
- 强约束识别准确率：不低于 90%
- 必须人工样本识别准确率：不低于 90%
- 不允许出现错误强自动落码
- 业务人员认为解释可读比例：不低于 90%

### 9.2 扩展样本阶段指标

建议扩展到 100 到 200 条样本。

通过标准：

- JSON 输出有效率：不低于 98%
- 候选池 Top10 覆盖率：不低于 90%
- 候选池 Top20 覆盖率：不低于 95%
- 强自动落码错误率：目标 0，最高不得超过 1%
- 弱自动落码错误率：最高不得超过 2%
- 必须人工召回率：不低于 90%
- 偏差识别召回率：不低于 85%
- 遗漏识别召回率：不低于 85%

### 9.3 真实客户库试跑指标

试跑阶段应统计：

- 总记录数
- 成功处理数
- 模型错误数
- 强自动落码数
- 弱自动落码数
- 建议落码数
- 必须人工审核数
- 未匹配数
- 抽检错误数
- 平均单条耗时
- 平均单条模型成本

产品化前建议达到：

- 强自动落码抽检错误率：目标 0
- 弱自动落码抽检错误率：不高于 2%
- 人工审核认为解释有帮助比例：不低于 80%
- 模型错误率：不高于 2%

### 9.4 记忆系统指标

记忆系统应单独统计效果。

建议指标：

- 人工确认记忆命中率
- 客户表达习惯记忆命中率
- 商品语义记忆命中率
- 业务等价关系命中率
- 失败案例记忆触发次数
- 记忆命中后候选池覆盖率提升
- 记忆命中后模型调用减少比例
- 记忆支持弱自动落码数量
- 记忆导致错误判断数量

产品化前建议达到：

- 记忆导致错误判断数量：目标 0
- 所有支持弱自动落码的记忆必须有人工作为来源
- 失败案例记忆触发后不得继续强自动落码
- 记忆命中记录必须可追溯

## 10. 性能和成本指标

### 10.1 验证阶段

验证阶段不追求速度。

建议指标：

- 单条处理时间：10 到 60 秒可接受
- 30 条黄金样本总耗时：30 分钟内可接受
- 优先保证输出质量和可排查性

### 10.2 原型阶段

建议指标：

- 单条平均处理时间：10 到 30 秒
- 100 条批处理时间：30 到 60 分钟
- 支持暂停、继续、失败重试

### 10.3 产品化阶段

产品化前再定最终指标。

初步建议：

- 单条平均处理时间：5 到 15 秒
- 1000 条处理时间：2 到 5 小时
- 支持后台批处理
- 支持断点续跑

### 10.4 成本控制

必须记录：

- 每条记录模型调用次数
- 每次输入 token
- 每次输出 token
- 每条估算成本
- 每批估算成本

如果成本过高，优先优化：

1. 候选池数量
2. Prompt 长度
3. 两段调用是否可合并
4. 历史关系命中后的模型调用减少
5. 产品记忆命中后的候选池收缩
6. 产品记忆命中后的 Prompt 精简

## 11. 安全和留痕

### 11.1 API Key

要求：

- 不写入源码
- 不写入 Git 仓库
- 从本地配置或环境变量读取
- 日志中不得打印完整 API Key

### 11.2 模型输入留痕

每次模型调用应保存：

- 任务 ID
- 记录 ID
- Prompt 版本
- 输入摘要
- 候选列表
- 模型名
- 调用时间
- 请求耗时
- token 用量

敏感信息后续如有要求，可做脱敏。

### 11.3 模型输出留痕

每次模型输出应保存：

- 原始输出
- 解析后 JSON
- 解析状态
- 风险标记
- 系统最终状态
- 是否人工改写

### 11.4 人工审核留痕

人工审核应保存：

- 审核人
- 审核时间
- 审核动作
- 原推荐结果
- 人工最终结果
- 审核备注
- 是否沉淀历史关系

## 12. 错误处理

### 12.1 模型错误

模型错误包括：

- 网络超时
- 接口限流
- 输出非 JSON
- JSON schema 校验失败
- 必填字段缺失

处理方式：

- 自动重试最多 2 次
- 重试失败后标记 `model_error`
- 不允许把模型错误记录自动落码

### 12.2 候选池错误

候选池为空：

- 标记 `unmatched` 或 `manual_review`
- 不允许大模型凭空猜编码

候选池过大：

- 截断到最大候选数
- 保留截断规则
- 标记候选池过大风险

### 12.3 JSON 校验失败

处理方式：

- 保存原始输出
- 尝试一次修复格式
- 修复失败后标记 `model_error`
- 不进入自动落码

## 13. 原型开发建议

### 13.1 原型优先级

第一优先级：

- 样本表导入
- 候选池展示
- 大模型输出展示
- 证据和风险展示
- 人工确认
- 导出

第二优先级：

- 历史关系沉淀
- 业务等价关系维护
- 批量任务管理
- 成本统计

第三优先级：

- 美化界面
- 权限管理
- 多人协作
- 性能优化

### 13.2 页面建议

最小原型页面：

- 数据导入页
- 字段映射页
- 样本/任务列表页
- 单条语义翻译详情页
- 人工审核页
- 导出页
- 运行日志页

### 13.3 单条详情页必须展示

- 客户原始记录
- 客户语义摘要
- 关键身份信号
- 强约束
- 弱约束
- 候选商品列表
- 每个候选的证据对齐
- 风险标记
- 模型建议结果
- 人工审核操作

## 14. 技术验收门槛

进入产品化前，必须至少满足：

- 完成 30 条黄金样本验证
- 完成 100 条以上扩展样本验证
- 候选池 Top20 覆盖率达到目标
- 大模型输出 JSON 稳定
- 强自动落码无明显错误
- 必须人工审核样本能被识别
- 业务人员能看懂模型解释
- 模型调用成本可接受
- 错误记录不会自动落码
- 产品记忆系统能记录人工确认关系
- 产品记忆系统能记录失败案例
- 记忆命中后能说明引用了哪条记忆
- 记忆不能无条件覆盖当前证据

如果以上门槛未达成，不建议进入正式产品开发。

## 16. 还需要继续确认的问题

以下技术问题还需要通过样本验证继续确认：

- 选择哪个大模型作为第一轮验证模型
- 两段式调用是否必须长期保留
- 候选池是否需要引入向量检索
- SQLite 是否足够支撑正式产品
- 原型是否继续用 Jinja2，还是进入 React 前端
- 自动落码阈值是否需要数值化
- 历史关系是否可以减少模型调用
- 产品记忆系统第一版是否只启用人工确认记忆和失败案例记忆
- 客户表达习惯记忆是否需要按客户隔离
- 商品语义记忆是否需要人工审核后才能启用
- 成本是否能被业务接受

## 17. 结论

二期技术路线应该围绕大模型主流程设计。

不是把大模型接到一期流程末端。

技术上最重要的不是先做复杂系统，而是先建立：

- 样本验证
- 稳定输入输出
- 候选池覆盖
- 证据对齐
- 风险分级
- 人工审核留痕
- 产品记忆系统

只有这些成立，二期才值得进入产品化。
