# 002.1号系统模型流程方案：结构化补强

版本：v0.1  
日期：2026-04-26  
状态：002 方案补强稿  

## 1. 补强目标

002 号方案已经确认：

**模型发令，系统执行；商品多轮入圈，失败回大自然；知识库只管别名和同义词；自动落码必须有证据。**

002.1 用来补齐 002 的可执行边界。

本补强稿解决七个问题：

1. 模型发什么令。
2. 入圈条件和排除条件怎么表达。
3. 大自然池如何避免无限回流。
4. 知识库中的词条如何分级。
5. 哪些环节调用模型，哪些环节不调用模型。
6. 自动落码如何变成机器可校验条件。
7. 如何同时减少人工和控制错码风险。

## 2. 模型发令格式

模型不能只输出自然语言命令。

模型发令必须转成结构化对象，系统只执行结构化命令。

### 2.1 批处理命令结构

建议字段：

```json
{
  "round_id": "round_001",
  "round_name": "核心品名_生抽",
  "round_goal": "优先处理疑似生抽商品",
  "entry_dimension": "core_product_name",
  "entry_terms": ["生抽"],
  "entry_alias_terms": ["酱油"],
  "exclude_terms": ["老抽", "蒸鱼豉油", "蚝油", "料酒"],
  "weak_related_terms": ["酱油"],
  "must_check_fields": ["核心品名", "品牌", "规格", "单位", "包装"],
  "hard_conflict_fields": ["核心品名", "品牌", "规格", "单位", "包装"],
  "search_strategy": {
    "company_catalog_scope": "global",
    "candidate_limit": 20,
    "export_candidate_limit": 5
  },
  "model_compare_policy": "compare_only_after_candidates",
  "auto_code_policy": "system_gate_required"
}
```

### 2.2 字段含义

| 字段 | 含义 |
|---|---|
| `round_id` | 本轮处理编号 |
| `round_name` | 给人看的本轮名称 |
| `round_goal` | 本轮想处理什么问题 |
| `entry_dimension` | 本轮入圈维度 |
| `entry_terms` | 入圈关键词 |
| `entry_alias_terms` | 可用于扩展搜索的别名词 |
| `exclude_terms` | 明确排除词 |
| `weak_related_terms` | 相关但不能等同的词 |
| `must_check_fields` | 候选比较时必须检查的身份字段 |
| `hard_conflict_fields` | 一旦冲突就不能自动落码的字段 |
| `search_strategy` | 系统检索策略 |
| `model_compare_policy` | 模型比较策略 |
| `auto_code_policy` | 自动落码策略 |

系统必须校验模型命令结构。

如果命令缺少关键字段，系统不执行该命令，应要求模型重试或把该轮转入疑难策略。

## 3. 入圈条件和排除条件

每一轮必须同时有：

- 入圈条件。
- 排除条件。
- 硬冲突检查字段。

只有入圈条件，没有排除条件，不允许作为正式批处理命令。

### 3.1 入圈不是落码

入圈只说明：

**这条商品本轮可以参加这一类共同特征处理。**

入圈不表示：

- 已经匹配。
- 可以落码。
- 可以跳过候选比较。
- 可以跳过安全校验。

### 3.2 排除条件示例

| 本轮处理圈 | 入圈词 | 排除词 | 说明 |
|---|---|---|---|
| 番茄/西红柿 | 番茄、西红柿 | 番茄酱、番茄沙司、番茄汁、番茄锅底 | 防止新鲜蔬菜和加工品误配 |
| 生抽 | 生抽 | 老抽、蒸鱼豉油、蚝油、料酒 | 防止调味品大类下误配 |
| 可乐 | 可乐 | 可乐味、可乐鸡翅调料 | 防止口味词误配 |
| 牛奶 | 牛奶 | 牛奶味、奶糖、奶茶 | 防止原品和风味品误配 |
| 500ml瓶装 | 500ml、500毫升 | 500g、500克、箱、桶 | 防止容量和重量、单瓶和整箱混淆 |

### 3.3 错圈回流规则

如果商品入圈后出现以下情况，应回流大自然池，而不是强行落码：

- 只有字面相似，没有商品身份一致证据。
- 命中排除词。
- 候选只有大类相关，没有具体品名一致。
- 规格、单位或包装不清楚。
- 模型无法解释为什么是同一商品身份。

## 4. 多轮维度选择

002 中给出的顺序是：

名称 -> 品牌 -> 规格包装 -> 别名 -> 疑难

002.1 修正为：

**维度顺序由模型建议，但只能在系统允许的维度列表中选择。**

### 4.1 系统允许的入圈维度

第一版只允许以下维度：

- `core_product_name`：核心品名。
- `brand`：品牌。
- `alias_synonym`：别名和强同义词。
- `spec_unit`：规格和单位。
- `package_form`：包装形态。
- `series_marker`：系列、等级、厂家标识。
- `flavor_form`：口味、形态。
- `hard_case`：疑难逐条处理。

模型不能发明新的维度。

如需新增维度，应先进入文档评审，再进入开发。

### 4.2 维度选择原则

模型选择本轮维度时，应优先考虑：

- 该维度能覆盖多少剩余商品。
- 该维度是否能明显缩小候选范围。
- 该维度是否有可靠别名或同义词支持。
- 该维度是否容易产生错配风险。
- 该维度处理后能否明显减少大自然池数量。

### 4.3 系统对模型维度建议的限制

系统只接受：

- 在允许维度列表内的建议。
- 带有入圈词和排除词的建议。
- 带有必须检查字段的建议。
- 带有候选数量上限的建议。

否则系统应拒绝执行，并记录为模型发令不合格。

## 5. 大自然池回流终止规则

大自然池不能无限循环。

每条客户商品必须记录：

- 已参与轮次数。
- 已参与维度。
- 每轮失败原因。
- 是否命中过排除词。
- 是否出现过候选不足。
- 是否出现过候选冲突。

### 5.1 最大回流次数

第一版建议：

```text
同一商品最多参与 5 轮入圈。
同一维度最多参与 2 次。
同一商品最多触发 2 次模型逐条比较。
```

超过上限仍未完成，应进入疑难池。

### 5.2 疑难池进入条件

出现以下情况，进入疑难池：

- 已达到最大入圈次数。
- 多轮候选都不足。
- 多轮候选互相冲突。
- 模型多次给出不同建议。
- 规格、单位、包装无法从客户记录中确认。
- 客户商品疑似我司库缺失。

### 5.3 疑难池处理

疑难池不是马上人工。

疑难池的处理顺序：

1. 模型逐条精细判断。
2. 系统重新尝试全局检索。
3. 如仍不可靠，导出 Excel 给人工处理。

## 6. 知识库词条分级

知识库只做别名和同义词，但必须分级。

### 6.1 词条类型

| 类型 | 示例 | 作用 | 是否可增强自动落码证据 |
|---|---|---|---|
| 强同义 | 番茄 = 西红柿 | 表示商品表达等价 | 可以 |
| 地区别名 | 土豆 = 马铃薯 | 表示不同地区叫法 | 可以 |
| 品牌别名 | HT = 海天 | 表示品牌表达等价 | 可以 |
| 规格等价 | 500ml = 500毫升 = 0.5L | 规格换算 | 可以 |
| 弱相关 | 生抽 ~ 酱油 | 扩展检索 | 不可以 |
| 上下位 | 生抽 属于 酱油类 | 扩展检索和解释 | 不可以 |
| 系列标识 | 金标、银标、特级 | 身份辅助信号 | 只可辅助 |
| 口味形态 | 原味、草莓味、切片、整颗 | 身份辅助信号 | 只可辅助 |

### 6.2 知识库状态

词条还应有状态：

| 状态 | 含义 | 是否参与自动落码 |
|---|---|---|
| `suggested` | 模型建议，未确认 | 不参与 |
| `trial` | 试用中，只辅助检索 | 不直接参与 |
| `confirmed` | 已确认 | 可作为证据之一 |
| `blocked` | 禁用或证明错误 | 不参与 |

### 6.3 知识库安全原则

- `suggested` 词条不能参与自动落码。
- `trial` 词条只能帮助召回候选。
- 只有 `confirmed` 强同义、品牌别名、规格等价，才可增强自动落码证据。
- 弱相关、上下位关系永远不能单独支持自动落码。
- 知识库词条必须保留来源、创建时间、最后验证时间。

## 7. 模型调用成本策略

模型调用分为四档。

### 7.1 零模型调用

以下情况不调用模型：

- 人工已确认且当前我司库编码仍有效。
- 强同义词和规格等价已经确认，且候选唯一。
- 明显品牌、规格、单位、包装硬冲突。
- 该商品已超过最大处理轮次，准备进入导出人工处理。

### 7.2 批次发令调用

模型看剩余池概况，输出本轮处理命令。

适用于：

- 每一轮开始前。
- 大自然池规模仍较大时。
- 需要选择下一轮入圈维度时。

### 7.3 候选比较调用

模型只看：

- 当前客户商品必要字段。
- Top 候选必要字段。
- 当前入圈命令。
- 已确认知识库摘要。

适用于：

- 系统已经找到多个候选。
- 候选相似但无法靠硬规则区分。

### 7.4 疑难逐条调用

只用于疑难池。

适用于：

- 多轮回流后仍未完成。
- 候选冲突严重。
- 客户表达极乱。

### 7.5 调用预算建议

第一版建议记录：

- 每轮模型发令次数。
- 每条商品模型比较次数。
- 每个任务总模型调用次数。
- 每百条商品平均调用次数。
- 每轮自动完成率。
- 每轮回流率。

这些指标用于判断 002.1 是否真的省成本。

## 8. 自动落码机器校验条件

自动落码不能只靠模型置信度。

系统必须能机器校验。

### 8.1 自动落码最低条件

一条结果要自动落码，至少满足：

1. 推荐编码真实存在于当前我司商品库。
2. 核心品名一致，或存在 `confirmed` 强同义关系。
3. 如果客户和候选都有品牌，品牌必须一致或存在 `confirmed` 品牌别名。
4. 如果客户和候选都有规格，规格必须一致或可换算等价。
5. 如果客户和候选都有单位，单位必须一致或存在明确包装换算。
6. 包装形态不能明显冲突。
7. 模型必须给出中文证据摘要。
8. 证据必须能追溯到客户原文、我司商品库字段或已确认知识库。
9. 未命中本轮排除条件。
10. 没有命中硬冲突字段。

### 8.2 禁止自动落码条件

只要出现以下任一情况，禁止自动落码：

- 核心品名冲突。
- 品牌明确冲突。
- 规格明确冲突。
- 单位或包装明确冲突。
- 客户备注中存在改变商品身份的信息。
- 模型推荐了不存在的编码。
- 模型理由无法追溯到原始字段。
- 候选之间差距不足，无法唯一确定。
- 知识库仅有弱相关或上下位关系支撑。
- 该商品本轮命中过排除词。

### 8.3 状态降级

系统应按风险从高到低决定状态：

1. 命中硬冲突：必须人工审核。
2. 无可靠候选：未找到可靠匹配。
3. 证据充分且无冲突：自动落码。
4. 证据较充分但有表达差异：自动落码但有表达差异。
5. 候选较像但不足以自动：建议落码待确认。

## 9. 人工减少指标和错码红线

三期目标是减少人工，但不能用错码换人工减少。

### 9.1 必须统计的指标

每轮任务必须统计：

- 客户商品总数。
- 自动落码数量。
- 自动落码但有表达差异数量。
- 建议落码待确认数量。
- 必须人工审核数量。
- 未找到可靠匹配数量。
- 大自然池回流数量。
- 疑难池数量。
- 模型调用次数。
- 人工处理后再次成功数量。

### 9.2 成功方向

系统每轮迭代应追求：

- 自动完成率上升。
- 人工干预率下降。
- 同类问题重复出现次数下降。
- 知识库命中率上升。
- 候选漏召回率下降。

### 9.3 错码红线

以下指标优先级高于自动化率：

- 自动落码严重错误必须为 0。
- 严重错误包括核心品名错、品牌冲突、规格包装冲突、系统或模型脑补客户未表达信息。
- 不能为了减少人工，把建议落码待确认伪装成自动落码。
- 不能为了提高完成率，把未找到可靠匹配伪装成有编码。

## 10. 开发落地建议

002.1 落地时建议拆成以下模块：

| 模块 | 责任 |
|---|---|
| `RoundPlanner` | 接收模型发令，校验批处理命令 |
| `NaturePool` | 管理大自然池、回流次数、疑难池 |
| `KnowledgeLexicon` | 管理别名和同义词分级 |
| `CandidateExecutor` | 根据模型命令执行检索 |
| `CandidateComparator` | 调用模型比较客户商品和候选 |
| `AutoCodeGate` | 自动落码机器校验 |
| `RunMetrics` | 统计成本、回流、人工干预和错码指标 |

第一版不需要把模块都做复杂。

但代码边界必须按这些责任拆开，否则后面会再次变成一团乱。

## 11. 002.1 结论

002.1 的核心补强是：

**模型可以发令，但只能发结构化命令；商品可以入错圈，但必须有排除条件和回流机制；系统可以自动落码，但必须通过机器可校验的安全门；知识库可以帮忙，但只保存分级后的别名和同义词。**

这使 002 从“聪明想法”变成“可开发方案”。
