## 1. 技术目标

三期 3.1 的技术目标不是一次性做完整智能审核工作台。

三期 3.1 只先把最小主线做稳：

**初始化配置 -> 更新我司商品库 -> 新建对照任务 -> 对照进度看板 -> 导出多工作表 Excel -> 人工加工后开始下一轮。**

技术方案必须服务这个目标。

第一版优先保证：

- 能在本机稳定启动。
- 能读取中文路径和中文文件名 Excel。
- 能保存配置和任务记录。
- 能跑完一轮对照任务。
- 能暂停、继续、停止任务。
- 能导出业务人员可用的多工作表 Excel。
- 能根据人工加工后的 Excel 开始下一轮。
- 模型不可用时不伪造智能结果。

## 2. 总体架构

三期 3.1 采用：

**Tauri 桌面壳 + Web 前端 + Python 本地服务。**

整体结构：

```text
Tauri 桌面壳
  -> Web 前端工作台
      -> Python 本地服务
          -> SQLite 本地数据库
          -> Excel 读取和导出
          -> 候选生成
          -> 模型调用
          -> 任务运行和日志
```

说明：

- Tauri 负责桌面窗口、应用生命周期和打包。
- Web 前端负责界面和用户交互。
- Python 本地服务负责所有业务计算和文件处理。
- SQLite 负责本地任务状态、商品库索引、字段映射、运行结果和日志索引。
- Excel 文件仍保留为业务人员主要加工载体。

正式用户体验中，不暴露浏览器、端口号或命令行。

内部通信可以使用本机 `127.0.0.1` 动态端口，但这只是内部实现细节。

- `phase3_app/` 是后续真正落代码的新工程。

## 4. 技术栈选择

### 4.1 桌面壳

选择：

**Tauri。**

职责：

- 提供桌面应用窗口。
- 启动和监控 Python 本地服务。
- 加载 Web 前端。
- 管理应用退出时的本地服务关闭。
- 后续负责打包成可双击运行的桌面应用。

第一版不让业务用户手动打开浏览器访问 `127.0.0.1`。

### 4.2 Web 前端

建议：

**Vite + React + TypeScript。**

原因：

- 适合做 Codex 类工作台界面。
- 页面状态和任务状态更容易组织。
- 后续做设置窗口、任务看板、历史任务和审核工作台时可扩展。
- TypeScript 有利于约束前后端数据结构。

前端第一版页面：

- 首页工作台
- 初始化配置 / 系统设置
- 更新我司商品库
- 新建对照任务
- 对照进度看板
- 导出 Excel / 下一轮提示

3.1 不做：

- 页面明细表
- 页面候选解释工作台
- 页面人工审核工作台

### 4.3 Python 本地服务

建议：

**FastAPI + Uvicorn + SQLite + openpyxl + httpx。**

职责：

- Excel 读取和预览。
- 中文路径和中文文件名自检。
- 我司商品库导入和索引。
- 客户商品库导入和字段预判。
- 字段确认保存。
- 任务创建和轮次管理。
- 候选生成。
- 模型调用。
- 证据对齐结果结构化。
- 对照进度统计。
- 暂停、继续、停止。
- 多工作表 Excel 导出。
- 人工加工 Excel 回导和第二轮处理。

说明：

- Python 服务只绑定本机。
- 不做公网服务。
- 不做 SaaS。
- 不让业务用户直接接触 Python 服务。


## 6. 配置方案

### 6.1 配置内容

系统配置至少包括：

- 模型是否启用。
- 模型提供方。
- Base URL。
- 模型名称。
- 请求超时。
- 失败重试次数。
- 默认数据目录。
- 默认导出目录。
- 是否保存模型请求和返回。
- 是否启用详细日志。

### 6.2 API Key 保存

API Key 不写入：

- 源码
- Git 仓库
- 示例配置
- 普通日志

建议方案：

- 开发期可支持环境变量读取，例如 `DEEPSEEK_API_KEY`。
- 正式应用优先使用系统凭据存储，例如 Windows Credential Manager。
- 非敏感配置保存为本地 JSON。
- 前端只显示 API Key 是否已配置，不显示完整值。

### 6.3 配置自检

初始化配置时必须检查：

- 模型配置是否完整。
- 模型连接是否成功。
- 默认目录是否可读写。
- 中文文件名和中文路径是否可用于导入导出。
- SQLite 数据库是否可写。
- 日志目录是否可写。

界面文案应使用：

**文件导入导出自检**

不要让业务用户理解“UTF-8”“中文路径编码”等技术词。

## 7. 前后端通信

### 7.1 通信方式

建议：

**Web 前端通过 HTTP 调用 Python 本地服务。**

实现方式：

- Tauri 启动 Python 服务。
- Python 服务绑定 `127.0.0.1` 动态端口。
- Tauri 获取端口后传给前端。
- 前端通过该地址调用 API。

用户不看到端口。

如果服务启动失败，前端只显示中文错误：

`本地服务启动失败，请重启应用或查看日志。`

### 7.2 服务生命周期

Tauri 负责：

- 启动 Python 服务。
- 等待 `/health` 返回成功。
- 将服务地址交给前端。
- 监听服务异常退出。
- 应用退出时关闭 Python 服务。

Python 服务负责：

- 接受本机请求。
- 执行业务任务。
- 写入数据库和日志。

## 10. 任务状态设计

### 10.1 运行状态

`task_runs.status` 建议取值：

- `created`
- `running`
- `paused`
- `stopping`
- `stopped`
- `completed`
- `failed`

导出按钮规则：

- `completed` 才能导出正式 Excel。
- `running`、`paused`、`stopping`、`stopped`、`failed` 都不能导出正式结果。

### 10.2 结果状态

业务状态仍保留五档：

- 自动落码
- 自动落码但有表达差异
- 建议落码待确认
- 必须人工审核
- 未找到可靠匹配

运行看板统计分组：

- 自动落码无风险：对应 `自动落码`
- 建议落码需复核：对应 `自动落码但有表达差异` 和 `建议落码待确认`
- 必须人工干预：对应 `必须人工审核`
- 未找到可靠匹配：对应 `未找到可靠匹配`

这样既保留业务判断细度，也让看板更好懂。

## 11. Excel 读取方案

### 11.1 读取工具

第一版优先使用：

**openpyxl。**

原因：

- 支持 `.xlsx`。
- 支持保留工作簿结构。
- 支持写入多工作表。
- 支持内部超链接。
- 适合做导出模板。

`pandas` 可作为辅助分析工具，但不作为第一版唯一依赖。

### 11.2 读取规则

导入 Excel 时读取：

- 工作表名称。
- 表头行。
- 数据行数。
- 列名。
- 列索引。
- 样例值。
- 重复列名。
- 空白列。

重要原则：

- 字段映射必须记录列索引，不能只靠列名。
- 因为客户库可能有重复列名。
- 原始行号必须保留。
- 原始单元格值尽量不修改。

### 11.3 中文文件名自检

初始化时创建临时中文文件，例如：

```text
中文文件名自检.xlsx
```

检查：

- 能否写入。
- 能否读取。
- 能否删除。
- 日志是否乱码。

界面只显示：

`文件导入导出自检通过。`

## 12. 多工作表 Excel 导出方案

### 12.1 导出原则

导出 Excel 必须：

- 不覆盖原始 Excel。
- 保留客户原始列。
- 尽量保留客户原始行顺序。
- 在原始列后追加少量关键结果列。
- 生成详细证据表。
- 生成统计汇总表。
- 保留系统任务行ID。

### 12.2 工作表一：对照结果总表

用途：

业务人员主要处理表。

结构：

- 客户原始列
- 系统任务行ID
- 原始行号
- 对照状态
- 我司商品编码
- 我司商品名称
- 是否需要人工审核
- 推荐理由简述
- 风险提示简述
- 查看详细证据
- 人工确认结果
- 人工审核备注

### 12.3 工作表二：详细证据表

用途：

查看每条结果为什么这样推荐。

结构：

- 系统任务行ID
- 原始行号
- 客户商品名称
- 推荐我司商品
- 证据对齐摘要
- 对上的信息
- 没对上的信息
- 风险详情
- 备选候选 1
- 备选候选 2
- 备选候选 3
- 返回总表

### 12.4 工作表三：统计汇总表

用途：

查看本轮整体结果。

结构：

- 当前任务名称
- 当前轮次
- 我司商品库总数
- 客户商品库总数
- 自动落码无风险数量
- 建议落码需复核数量
- 必须人工干预数量
- 未找到可靠匹配数量
- 本轮开始时间
- 本轮完成时间
- 使用模型
- 我司商品库版本或更新时间

### 12.5 隐藏工作表：系统元数据

建议增加隐藏工作表：

`_系统元数据`

用于保存：

- task_id
- run_id
- round_no
- catalog_version_id
- export_version
- exported_at

这样人工加工后回导时，系统能更稳定识别来源。

### 12.6 内部链接

使用 openpyxl 写入内部链接。

示例概念：

```text
对照结果总表!X2 -> 详细证据表!A2
详细证据表!L2 -> 对照结果总表!A2
```

业务效果：

- 总表不需要横向塞满所有解释。
- 用户需要原因时，点击“查看详细证据”。
- 看完后可以点击“返回总表”。

## 13. 候选生成第一版策略

3.1 候选生成不追求最终智能定型。

第一版目标：

**尽量不要漏掉可能正确的候选，并把风险说清楚。**

### 13.1 文本归一

对客户和我司商品生成 `search_text`。

归一内容：

- 去除多余空格。
- 统一大小写。
- 全角半角归一。
- 常见标点归一。
- 规格符号归一，例如 `*`、`×`、`x`。
- 单位轻量归一，例如 `ml`、`毫升`。
- 保留原始文本，不覆盖原始值。

### 13.2 候选召回

第一版候选来源：

- 商品名称包含关系。
- 核心词相似。
- 品牌词命中。
- 规格词命中。
- 单位命中。
- RapidFuzz 字符串相似度。
- 历史人工结果作为提示，不能直接覆盖当前证据。

候选数量：

- 内部保留 Top 20。
- 导出 Excel 展示 Top 3 到 Top 5。

### 13.3 候选排序

候选排序参考：

- 核心品名相似度。
- 品牌是否一致。
- 规格是否一致。
- 单位是否一致。
- 描述和备注是否支持。
- 是否存在明显冲突。

候选生成不直接决定最终状态。

最终状态必须经过证据对齐和风险识别。

## 14. 模型调用方案

### 14.1 模型定位

模型用于：

- 整理客户记录语义。
- 比较客户记录和候选是否表达同一商品身份。
- 输出中文推荐理由。
- 输出风险提示。
- 输出结构化状态建议。

模型不应单独决定自动落码。

系统需要对模型输出做结构校验和业务规则校验。

### 14.2 模型请求边界

发送给模型的数据应尽量最小化。

建议只发送：

- 当前客户行必要字段。
- Top 候选的必要字段。
- 字段确认结果。
- 当前判断准绳摘要。

默认不发送：

- 无关列。
- 完整客户 Excel。
- API Key。
- 本地文件路径。

### 14.3 输出结构

模型输出必须转成结构化 JSON。

建议字段：

- `selected_candidate_index`
- `status`
- `reason_summary`
- `evidence_summary`
- `risk_summary`
- `matched_signals`
- `unmatched_signals`
- `conflict_signals`
- `need_manual_review`

如果模型输出结构不合法：

- 不使用该输出自动落码。
- 该行进入“必须人工审核”或“未找到可靠匹配”。
- 记录模型输出异常。

### 14.4 业务规则校验

模型返回后，系统再做规则校验。

必须拦截：

- 核心品名冲突却自动落码。
- 品牌冲突却自动落码。
- 规格或包装可能影响结算却自动落码。
- 需要脑补客户没写的信息却自动落码。
- 未找到可靠匹配却输出确定编码。

## 15. 运行看板和任务控制

### 15.1 后台任务执行

Python 服务维护任务执行器。

每个 run 按行处理客户记录。

处理流程：

1. 读取 task rows。
2. 生成候选。
3. 调用模型或本地规则。
4. 校验结果。
5. 写入 `run_results`。
6. 更新 `task_runs.completed_count`。

### 15.2 暂停

暂停规则：

- 设置 run 状态为 `paused`。
- 当前正在处理的行完成后停止取下一行。
- 已完成结果保留。

### 15.3 继续

继续规则：

- 将 `paused` 改回 `running`。
- 从未完成行继续。

### 15.4 停止

停止规则：

- 设置停止标记。
- 当前行处理完后停止。
- run 状态变为 `stopped`。
- 本轮不允许导出正式 Excel。

### 15.5 看板轮询

前端通过轮询获取状态。

建议：

- 运行中每 1 秒轮询一次。
- 暂停或完成后降低频率。
- 后续可改为 WebSocket，但 3.1 不强求。

## 16. 第二轮闭环

### 16.1 人工加工 Excel 回导

用户在 Excel 中加工后，系统通过“继续历史任务 / 开始下一轮”导入。

系统读取：

- `_系统元数据`
- 系统任务行ID
- 人工确认结果
- 人工审核备注
- 人工修改的我司商品编码
- 是否标记无匹配或需新增

### 16.2 回导校验

校验规则：

- task_id 是否存在。
- run_id 是否对应当前任务。
- task_row_id 是否能匹配。
- 人工填写的我司编码是否存在于最新我司库。
- 人工确认结果是否为空。
- 是否存在无法识别的行。

### 16.3 第二轮处理

第二轮基于：

- 原客户记录。
- 第一轮系统结果。
- 人工加工结果。
- 最新我司商品库。

规则：

- 人工已确认的行默认锁定，不被系统随意覆盖。
- 人工指定我司编码但编码不存在，标记为风险。
- 第一轮未匹配但我司库已补全的，重新生成候选。
- 人工标记无匹配的，下一轮保留人工意见并继续提示。

## 19. 打包方案

### 19.1 开发模式

开发模式：

```text
启动 Python 本地服务
启动 Web 前端开发服务
启动 Tauri 桌面壳
```

开发模式可以暴露端口给开发人员。

业务用户不接触开发模式。

### 19.2 打包模式

打包模式建议：

- Web 前端构建为静态资源。
- Python 服务用 PyInstaller 打包为本地 sidecar。
- Tauri 启动 sidecar。
- 应用退出时关闭 sidecar。

打包细节在工程执行计划中进一步验证。

## 20. 风险和控制

### 20.1 Tauri 与 Python 打包风险

风险：

- Python sidecar 打包体积较大。
- Windows 环境可能缺运行库。
- 路径和权限可能出问题。

控制：

- 尽早做空壳打包验证。
- 先验证健康检查。
- 不等业务功能写完才验证打包。

### 20.2 模型输出不稳定风险

风险：

- 模型输出格式不稳定。
- 模型可能给出不该自动落码的建议。

控制：

- 强制 JSON 结构校验。
- 业务规则二次拦截。
- 模型异常时进入人工审核或未匹配。

### 20.3 Excel 回导风险

风险：

- 人工可能删除系统任务行ID。
- 人工可能改乱表头。
- 人工可能排序、筛选、复制粘贴。

控制：

- 系统任务行ID必须保留。
- 增加隐藏元数据表。
- 回导时做严格校验。
- 无法匹配的行明确提示，不静默处理。

## 21. 3.1 不做清单

3.1 不做：

- 页面明细列表。
- 页面候选解释工作台。
- 页面人工审核工作台。
- 多人协同。
- 权限体系。
- 完整记忆系统。
- 向量召回定型。
- 模型精调。
- 云端 SaaS。

这些能力后续 3.2、3.3、3.4 再讨论。
