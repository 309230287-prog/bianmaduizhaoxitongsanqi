## 1. 文档目的

本文档用于定义三期商品编码对照系统的产品需求。

三期不是一期修补，也不是旧二期继续开发。

三期从已经确认的业务共识重新开始：

**系统要把客户商品语言翻译成我司商品语言，再落到我司商品编码。**

本文档主要回答：

- 产品到底是什么
- 给谁使用
- 解决什么业务问题

- 用户如何完成一轮编码对照
- 什么结果算正确
- 什么情况可以自动落码
- 什么情况必须人工审核
- 输出结果应该长什么样
- 第一版如何验收

## 3. 产品定义

### 3.1 产品名称

面向业务人员的产品名称为：

**商品编码对照系统。**

### 3.2 产品内核

产品底层逻辑为：

**商品语义翻译 + 证据对齐。**

它不是普通商品匹配工具。

普通匹配工具主要问：

**哪条最像？**

三期系统主要问：

**客户商品和我司候选是不是同一个业务商品身份？证据够不够？有没有关键差异？**

### 3.3 一句话说明

客户给一条商品记录，系统先理解这条记录在表达什么，再去我司商品库里找表达同一商品身份的候选，最后给出我司编码、中文解释和审核状态。

## 4. 项目背景

客户商品库和我司商品库之间经常存在表达差异。

客户商品库可能存在：

- 字段不完整
- 字段重复
- 名称中混入规格
- 规格格式不统一
- 单位和包装混用
- 备注中包含关键身份信息
- 类别口径与我司不一致
- 历史加工痕迹明显

我司商品库也不是完全干净的标准词条库。

我司商品名称和描述中可能包含：

- 品牌
- 品名
- 系列或等级
- 规格
- 包装层级
- 单位
- 形态或加工信息
- 管理编码尾巴
- 其他修饰词

因此，三期要解决的问题不是“把脏客户库匹配到干净我司库”。

三期真正要解决的是：

**客户记录中的复合语义，如何可靠对齐到我司商品库中的复合语义。**

## 5. 核心业务问题

系统需要帮助业务人员回答：

- 客户这条商品记录到底表达什么商品？
- 哪些信息是商品身份的一部分？
- 哪些信息只是辅助判断？
- 哪些信息可能是噪声？
- 客户记录和我司候选是否表达同一个业务商品身份？
- 差异是表达差异，还是商品身份差异？
- 是否可以自动落码？
- 是否必须人工审核？
- 如果人工审核，审核人员应该看什么证据？

## 6. 使用对象

主要使用对象包括：

- 采购人员
- 销售支持人员
- 商品资料维护人员
- 客户商品对照人员
- 内部运营人员

系统不应假设使用者具备技术背景。

系统输出必须使用业务人员能看懂的中文表达。

## 7. 产品目标

### 7.1 第一目标

**尽量减少错配、误译和关键语义遗漏。**

系统不能为了提高自动落码率而牺牲正确性。

尤其要避免：

- 把生抽翻成老抽
- 把单瓶翻成整箱
- 把品牌词识别错
- 把系列或等级词丢掉
- 忽略备注中的加工形态
- 根据客户没有写的信息擅自脑补

### 7.2 第二目标

**降低人工审核成本。**

系统不是取消人工审核，而是让人工审核从“重新找答案”变成“确认系统证据是否成立”。

### 7.3 第三目标

**沉淀可复用的业务经验。**

系统应逐步沉淀：

- 人工确认关系
- 客户表达习惯
- 商品语义知识
- 业务等价关系
- 失败案例

但这些记忆必须有适用范围，不能无条件套用。

## 8. 非目标

三期第一版不追求：

- 所有商品全部自动落码
- 完全取消人工审核
- 只靠字符串相似度完成对照
- 只靠模型置信度决定结果
- 把客户商品强制拆成固定字段后才允许判断
- 把我司商品库改造成纯净标准词条库
- 复杂多人协同
- 完整审批流
- 大规模自动学习
- 模型精调
- SaaS 化部署
- 提前绑定具体模型厂商或技术路线

## 9. 核心概念

### 9.1 商品身份

商品身份指一条商品在业务上到底是什么。

商品身份通常由多个语义信号共同决定。

这些信号可能包括：

- 品名
- 品牌
- 系列
- 等级
- 规格
- 包装层级
- 单位
- 形态
- 加工方式
- 产地
- 类别
- 备注补充信息

不同商品的身份决定因素不固定。

有的商品只需要 1 到 2 个强信号。

有的商品需要 5 到 6 个参数组合。

### 9.2 翻译正确

翻译正确指：

**客户记录表达的业务商品身份，和我司某条商品表达的业务商品身份一致。**

最低要求：

- 核心品名不能错
- 品牌不能冲突
- 规格和包装不能影响结算
- 单位不能造成误解
- 客户给出的关键信息都被解释
- 系统不能脑补客户没写的信息
- 最终落到的是我司真正可采购、可结算、可发货的商品

### 9.3 偏差

偏差指系统把客户原始意思理解歪了。

典型偏差包括：

- 把品牌、品名、系列、等级角色认错
- 把单瓶和整箱混掉
- 把弱信号当强信号
- 根据客户没写的信息擅自补品牌、规格或系列

示例：

`海天金标生抽` 中，`海天` 是品牌，`生抽` 是品名，`金标` 更像系列、等级或厂家标识。

如果系统把 `金标` 当品牌，就是偏差。

### 9.4 遗漏

遗漏指客户记录明明提供了关键信息，但系统没有纳入判断。

典型遗漏包括：

- 备注写 `切丝`，系统只看 `瘦肉`
- 规格写 `1*24*330ml`，系统只看 `330ml`
- 名称里写了 `500ml`，系统因为规格列为空就忽略规格
- 我司描述里有补充限制，系统没有拿来对照

### 9.5 证据对齐

证据对齐指系统要说明客户记录中的关键信息，是否能在我司候选商品中得到解释。

系统不能只输出一个编码。

系统必须说明：

- 哪些信息对上了
- 哪些信息没有对上
- 哪些信息存在冲突
- 哪些信息暂时无法判断
- 为什么可以或不可以落码

## 10. 第一版范围

### 10.1 第一版最小闭环

三期第一版只做最小可用闭环：

1. 首次打开或配置异常时，完成系统初始化配置。
2. 上传我司商品库。
3. 上传客户商品库，或手工输入一条客户商品。
4. 确认字段含义。
5. 为客户商品生成我司候选。
6. 输出中文解释和风险提示。
7. 给出五档中文状态。
8. 人工确认、修改或标记无匹配。
9. 导出编码对照结果 Excel。

第一版先做到：

**能用，能看懂，不乱落码，结果能被人工审核。**

### 10.2 第一版 In Scope

三期第一版应包含：

- 系统初始化配置检查
- 模型配置入口
- 基础参数配置入口
- 我司商品库 Excel 导入
- 客户商品库 Excel 导入
- 客户商品手工输入
- 表头和样例预览
- 字段含义确认
- 客户整行记录理解
- 我司候选生成
- 候选证据对齐
- 五档中文结果状态
- 中文推荐理由
- 中文风险提示
- 人工确认、修改、标记无匹配
- 导出编码对照结果 Excel
- 基础日志和异常提示
- 人工确认记录保存

### 10.3 第一版降级处理

以下能力第一版只做轻量版本，不做完整系统：

- 记忆系统：第一版先记录，不直接控制自动落码。
- 人工审核：第一版支持确认、修改、无匹配和备注，不做复杂审批流。
- 候选展示：第一版展示主要候选和备选候选，不做复杂多维分析。
- 统计分析：第一版只保留基础数量统计，不做高级报表。

### 10.4 第一版 Out of Scope

三期第一版暂不包含：

- 复杂多人协同审核
- 权限体系
- 审批流
- 云端 SaaS
- 模型精调
- 大规模自动学习
- 完整知识库管理后台
- 高级统计分析
- 自动替代全部人工判断
- 记忆直接决定自动落码

### 10.5 系统初始化配置

系统打开后，不应直接假设所有配置都已经可用。

第一版应有初始化配置检查。

初始化配置分为两种场景：

- 首次使用：用户需要完成必要配置后再进入正式业务流程。
- 日常使用：如果配置已经有效，系统直接进入工作台，并在页面上显示配置状态。

初始化配置至少包括：

- 模型服务是否启用
- 模型提供方
- Base URL
- API Key 来源或录入方式
- 模型名称
- 请求超时和失败重试等基础参数
- 默认数据目录
- 默认导出目录
- 日志保存位置
- 中文文件名和中文路径支持检查

第一版不要求一次性做复杂配置中心。

但必须做到：

- 用户知道当前模型是否可用。
- 用户知道 API Key 是否已配置。
- 用户知道当前使用哪个模型。
- 配置不可用时，系统不能悄悄进入模型判断流程。
- 没有模型配置时，系统应明确提示哪些能力不可用。
- API Key 不得写入源码或提交到仓库。

初始化配置不是业务对照本身。

它是业务流程前的系统准备步骤。

后续编写 3.1 业务流程文档时，应把流程拆成：

- A. 首次启动和初始化配置流程
- B. 日常商品编码对照流程

## 11. 三期分层需求框架

三期不能被当成一个一次性完成的大版本。

三期应拆成多个递进层次：

- 3.1 先跑通主线闭环
- 3.2 再补判断规则和验证样本
- 3.3 再做记忆系统和审核闭环
- 3.4 再做产品化工作台
- 3.5 再做技术增强和规模化

每一层都应有清楚交付物。

后一层不能反过来拖垮前一层。

### 11.1 三期 3.1 需求：主线闭环

3.1 的目标是先让整个业务主线跑通。

3.1 不追求系统很聪明。

3.1 只追求：

**能导入，能生成候选，能解释，能人工确认，能导出。**

3.1 应包含：

- 首次启动和初始化配置检查
- 我司商品库导入
- 客户商品库导入
- 单条客户商品手工输入
- 字段含义确认
- 候选生成
- 中文解释
- 五档中文状态
- 人工确认、修改、标记无匹配
- 结果导出 Excel
- 基础操作日志和异常提示

3.1 不应包含：

- 完整记忆系统
- 复杂审核流
- 多人协同
- 高级统计
- 大规模自动学习
- 技术路线复杂化
- 复杂模型管理中心

3.1 的成功标准是：

**业务人员能完成必要初始化，完成一轮真实编码对照，并能看懂系统为什么这样推荐。**

### 11.2 三期 3.2 需求：判断规则和验证样本

3.2 的目标是让系统判断有尺子。

3.1 只是跑通流程。

3.2 要回答：

- 什么算正确
- 什么算偏差
- 什么算遗漏
- 哪些情况自动落码
- 哪些情况必须人工审核
- 候选生成是否漏掉正确答案
- 系统解释是否能帮助人工审核

3.2 应包含：

- 业务商品身份判断表
- 核心身份信号、强约束、弱信号、噪声的定义
- 五档状态判定细则
- 判定优先级规则
- 验证样本表
- 样本标准答案
- 样本验收口径
- 候选质量检查

3.2 的成功标准是：

**系统不只是能跑，而是能用真实样本证明它没有明显乱判。**

### 11.3 三期 3.3 需求：记忆系统和审核闭环

3.3 的目标是让系统开始沉淀经验。

3.1 中的记忆只记录，不直接控制自动落码。

3.3 才逐步讨论记忆如何参与判断。

3.3 应包含：

- 人工确认记忆
- 客户表达习惯记忆
- 商品语义记忆
- 业务等价关系记忆
- 失败案例记忆
- 记忆适用范围
- 记忆和当前证据冲突时的处理方式
- 记忆撤销和修正机制
- 商品库版本变化后的记忆复核机制

3.3 的成功标准是：

**系统能把人工确认、等价关系和失败案例沉淀下来，但不会因为记忆而越学越歪。**

### 11.4 三期 3.4 需求：产品化工作台

3.4 的目标是让系统从可用变成好用。

3.4 应包含：

- 更清晰的首页工作台
- 我司商品库管理入口
- 客户商品库任务入口
- 手工输入入口
- 审核工作台
- 模型配置入口
- 日志和错误提示入口
- 导出记录
- 更完整的中文引导

3.4 的成功标准是：

**业务人员不需要开发人员在旁边解释，也能知道下一步该点哪里。**

### 11.5 三期 3.5 需求：技术增强和规模化

3.5 的目标是提升效果、速度和稳定性。

3.5 应晚于 3.1 和 3.2。

3.5 才讨论：

- 单模型还是多模型
- 是否引入向量召回
- 候选池优化
- 批量性能
- 本地数据库
- 更强的模型输出校验
- 更完整的任务队列
- 多客户模板管理
- 更完善的数据安全策略

3.5 的成功标准是：

**技术增强服务于已经验证过的业务流程，而不是让技术路线反过来牵着产品走。**

### 11.6 分层开发原则

三期分层开发应遵守：

- 先 3.1，后 3.2。
- 没有 3.1 主线闭环，就不做复杂记忆系统。
- 没有验证样本，就不做模型路线定型。
- 没有五档状态细则，就不扩大自动落码。
- 没有人工审核闭环，就不让记忆直接影响自动结果。
- 每一层都要能独立验收。

## 12. 字段含义确认要求

字段含义确认不应只是机械固定字段映射。

但为了让第一版可落地，字段需要分为三类。

### 12.1 必需字段

必需字段是系统运行的最低基础。

客户商品库最低必需：

- 客户商品名称

我司商品库最低必需：

- 我司商品编码
- 我司商品名称

如果缺少客户商品名称，系统不能对该客户记录进行商品语义判断。

如果缺少我司商品编码或我司商品名称，系统不能形成有效编码对照结果。

### 12.2 强建议字段

强建议字段不是每条都必须有，但缺失会影响结果等级。

强建议字段包括：

- 品牌
- 规格
- 单位
- 备注
- 分类
- 我司商品描述
- 我司商品别名

缺少强建议字段时，系统可以继续运行，但应提示风险。

如果缺失字段可能影响商品身份、价格、单位、包装或结算，系统应降低自动落码等级，必要时进入人工审核。

### 12.3 可选字段

可选字段包括：

- 客户编号
- 表格序号
- 是否中农网
- 历史业务标记
- 其他补充字段

可选字段可以辅助判断或追溯，但不能单独决定落码。

### 12.4 不参与判断字段

用户应能把明显无关的字段标记为不参与判断。

被标记为不参与判断的字段仍应保留在原始记录中，不能从导出文件中删除。

## 13. 五档结果状态和判定优先级

系统应输出五档中文业务状态。

五档状态不是并列随便选。

必须先判断高风险，再判断是否可以自动。

### 13.1 判定优先级总原则

状态判定优先级如下：

1. 先判断是否存在必须人工审核的风险。
2. 再判断是否没有可靠候选。
3. 再判断是否满足自动落码。
4. 再判断是否满足自动落码但有表达差异。
5. 最后判断是否为建议落码待确认。

只要出现核心风险，必须人工审核优先。

不能因为模型很自信、名称很像、历史曾经确认过，就覆盖当前明显风险。

### 13.2 自动落码

适用于：

- 证据完整
- 核心身份明确
- 强约束无冲突
- 第一候选明显可靠
- 不需要脑补
- 客户关键信息都能被候选解释

禁止用于：

- 核心品名不确定
- 品牌冲突
- 规格冲突
- 包装层级可能影响结算
- 需要补充客户没写的信息才能成立

### 13.3 自动落码但有表达差异

适用于：

- 存在表达差异
- 差异不影响业务商品身份
- 有人工确认或业务等价关系支撑
- 系统能解释差异为什么不影响落码

此状态必须留痕。

第一版中，此状态应谨慎使用。

如果表达差异可能影响商品身份、价格、单位、包装或结算，应转为必须人工审核。

### 13.4 建议落码待确认

适用于：

- 系统倾向明显
- 第一候选明显更强
- 没有发现严重冲突
- 但仍存在小范围不确定
- 需要人工快速确认

此状态不能被当成已确认编码。

导出中应明确标记为待确认。

### 13.5 必须人工审核

适用于：

- 核心品名不确定
- 品牌冲突
- 规格冲突
- 包装层级可能影响结算
- 单位换算不确定
- 备注可能改变商品身份
- 多个候选难以区分
- 系统需要脑补客户没写的信息
- 当前证据和历史记忆冲突

第一版宁愿多进人工审核，也不能乱自动落码。

### 13.6 未找到可靠匹配

适用于：

- 没有足够可靠的候选
- 候选均存在核心冲突
- 客户记录信息不足，无法判断

系统不能给此状态伪造确定编码。

## 14. 功能需求

### FR-01 我司商品库导入

系统应支持导入我司商品库 Excel。

第一版优先支持 `.xlsx`。

系统应读取：

- 工作表名称
- 表头
- 样例行
- 数据行数
- 主要字段
- 重复列
- 空白列

系统不应因为存在空白列或重复列名直接中断。

### FR-02 客户商品库导入

系统应支持导入客户商品库 Excel。

系统应读取：

- 工作表名称
- 表头
- 样例行
- 数据行数
- 商品相关字段
- 重复列
- 空白列
- 明显异常字段

客户商品库通常较乱，系统应以提示和确认为主，不应直接假设字段一定标准。

### FR-03 客户商品手工输入

系统应支持用户手工输入单条客户商品。

手工输入至少应支持：

- 商品名称
- 品牌
- 规格
- 单位
- 类别
- 备注
- 客户编号
- 其他补充信息

除商品名称外，其他字段可以为空。

系统应将手工输入记录视为一条完整客户商品记录。

### FR-04 字段含义确认

系统应支持用户确认客户库和我司库字段含义。

字段含义确认应支持：

- 自动建议字段含义
- 用户修改字段含义
- 标记字段不参与判断
- 标记补充字段
- 对缺失字段给出风险提示

字段确认结果应可保存为模板，便于同结构文件复用。

### FR-05 客户整行语义理解

系统应把客户一整行记录作为语义单元。

系统不应只看商品名称。

系统应综合以下信息：

- 名称
- 品牌
- 规格
- 单位
- 类别
- 编号
- 备注
- 其他补充列

系统应尽量识别：

- 核心品名
- 品牌
- 系列或等级
- 规格
- 包装层级
- 单位
- 形态
- 加工方式
- 产地
- 鲜冻状态
- 可能影响身份的备注

### FR-06 我司商品语义理解

系统不能把我司商品名称当成无需理解的标准答案。

系统应理解我司商品的：

- 商品编码
- 商品名称
- 别名
- 品牌
- 规格
- 单位
- 分类
- 描述
- 其他补充信息

系统应特别关注我司商品名称和描述中的：

- 品牌
- 品名
- 系列或等级
- 规格
- 包装结构
- 单位
- 形态或加工信息
- 管理编码尾巴
- 补充限制

### FR-07 候选生成

系统应为每条客户商品生成我司候选。

候选生成的目标是：

**尽量不要漏掉可能表达同一商品身份的候选。**

候选生成不负责最终拍板。

第一版候选生成要求：

- 每条客户商品应给出主要候选，或明确说明为什么没有候选。
- 页面和导出中建议展示 Top 3 到 Top 5 候选摘要。
- 系统内部可保留更多候选用于排错和复核。
- 每个候选必须保留来源说明。

候选来源说明可包括：

- 名称相似
- 核心品名一致
- 品牌一致
- 规格一致
- 单位一致
- 分类接近
- 历史确认
- 业务等价
- 人工曾经选择

候选为空时，系统必须说明原因。

### FR-08 证据对齐

系统应对客户记录和我司候选做证据对齐。

对齐内容至少包括：

- 核心品名是否一致
- 品牌是否一致、缺失或冲突
- 规格是否一致、可换算或冲突
- 包装层级是否一致
- 单位是否一致或可解释等价
- 系列或等级是否一致
- 形态或加工方式是否一致
- 备注是否影响身份
- 类别是否支持或冲突

系统应输出证据覆盖情况。

### FR-09 风险识别

系统应识别并标记风险。

风险包括：

- 核心品名不确定
- 品牌冲突
- 规格冲突
- 包装层级冲突
- 单位冲突
- 系列或等级冲突
- 备注可能改变身份
- 需要脑补客户未表达信息
- 多个候选都能解释客户记录
- 关键字段缺失
- 历史记忆和当前证据冲突

风险提示必须使用中文。

### FR-10 中文解释

系统不能只输出一个编码。

每条结果至少应输出：

- 推荐的我司商品
- 推荐理由
- 对上的关键信息
- 没对上的信息
- 风险提示
- 是否可自动落码
- 是否需要人工审核

解释语言应面向业务人员，不应使用大量技术术语。

### FR-11 人工审核

人工审核是正式流程的一部分。

系统应支持人工对结果进行：

- 确认推荐结果
- 改选其他候选
- 标记无匹配
- 修改结果状态
- 填写审核备注
- 标记系统理解错误
- 标记遗漏信息

人工审核后的结果应可以用于后续记忆沉淀。

### FR-12 结果导出

系统应基于客户原始 Excel 生成新文件。

系统不得覆盖原始文件。

导出结果应追加中文列。

建议追加列包括：

- 对照状态
- 我司商品编码
- 我司商品名称
- 我司品牌
- 我司规格
- 我司单位
- 推荐理由
- 证据对齐摘要
- 风险提示
- 备选候选
- 是否需要人工审核
- 人工确认结果
- 人工审核备注

对于“必须人工审核”和“未找到可靠匹配”，系统不能假装输出确定编码。

### FR-13 第一版记忆系统

系统应支持基础产品记忆。

第一版记忆边界如下：

- 第一版记忆先记录，不直接控制自动落码。
- 人工确认结果可以保存。
- 历史确认可以作为提示展示。
- 历史确认可以辅助候选排序。
- 历史确认不能无条件覆盖当前证据。
- 当前证据和历史记忆冲突时，应进入人工审核。

第一版至少记录：

- 客户原始记录
- 我司确认商品
- 人工确认人或确认来源
- 确认时间
- 确认理由
- 适用范围
- 是否允许未来作为自动落码依据

如果未来要让记忆参与自动落码，必须另行定义规则和验收标准。

### FR-14 基础日志和异常提示

系统应记录关键操作和异常。

至少包括：

- 文件导入
- 字段确认
- 候选生成
- 结果生成
- 人工审核
- 导出
- 异常失败

异常提示必须明确，不能静默写入错误结果。

## 15. 数据安全和模型边界

需求层必须先明确数据安全原则，不能全部留给技术方案。

### 15.1 原始文件安全

系统不得覆盖原始 Excel。

所有导出结果必须生成新文件。

### 15.2 API Key 安全

系统不得把真实 API Key 写入源码、默认配置文件或仓库。

API Key 的读取、保存和清理方式由后续技术方案细化。

### 15.3 外部模型调用边界

如果系统后续需要调用外部模型服务，应满足：

- 用户必须明确配置并启用模型服务。
- 系统应明确提示哪些数据会被发送给模型。
- 系统应尽量只发送完成判断所需的最小信息。
- 系统应避免把无关字段、敏感字段无提示地发送给外部模型。
- 模型请求和返回是否保存，应有开关或明确说明。

### 15.4 日志边界

日志不得默认记录完整 API Key。

如果日志保存模型请求或返回内容，应能被用户理解和管理。

涉及客户敏感数据的日志策略，应在技术方案中继续细化。

## 16. 数据输入

### 16.1 我司商品库

我司商品库是目标库。

可能使用的字段包括：

- 我司商品编码
- 我司商品名称
- 品牌
- 规格
- 单位
- 分类
- 别名
- 描述
- 其他补充字段

### 16.2 客户商品库

客户商品库是待翻译对象。

可能使用的字段包括：

- 客户商品名称
- 客户商品编号
- 品牌
- 规格
- 单位
- 类别
- 备注
- 其他补充字段

### 16.3 手工输入

手工输入用于处理单条客户商品。

手工输入应和客户 Excel 记录进入同一套判断流程。

## 17. 数据输出

系统主要输出：

- 编码对照结果表
- 中文解释
- 风险提示
- 人工审核结果
- 记忆沉淀记录
- 操作日志
- 异常日志

导出文件必须面向业务人员可读。

系统内部可以使用结构化字段，但界面和导出不应只展示英文枚举。

## 18. 非功能需求

### 18.1 易用性

业务人员应能按界面提示完成：

- 导入我司商品库
- 导入客户商品库
- 确认字段
- 查看推荐结果
- 完成人工审核
- 导出结果

系统不应要求用户理解模型、向量、召回、JSON 等技术概念。

### 18.2 可解释性

系统必须解释每条结果。

自动落码尤其必须有清晰解释。

### 18.3 稳定性

系统遇到失败时必须明确提示。

系统不能在失败、超时、异常输出时静默生成错误编码。

### 18.4 可追溯性

系统应保留：

- 输入记录
- 字段确认
- 候选来源
- 证据对齐摘要
- 结果状态
- 人工审核记录
- 记忆来源

### 18.5 可扩展性

三期第一版不提前锁死技术路线。

后续可以根据验证样本和产品效果决定：

- 单模型还是多模型
- 是否接向量召回
- 是否引入本地数据库
- 是否扩展记忆系统

## 19. 验证样本要求

进入技术方案前，应先建立验证样本表。

### 19.1 样本来源

第一批验证样本应从真实 Excel 中抽取。

优先使用：

- `我司商品库.xlsx`
- `客户商品库.xlsx`

### 19.2 样本数量

第一批建议先做小而准的样本表。

建议范围：

- 起步不少于 50 条
- 条件允许时扩展到 100 条

样本数量不是越多越好。

第一批样本的重点是覆盖风险类型，而不是追求全量代表性。

### 19.3 样本覆盖类型

验证样本应覆盖：

- 完全同名商品
- 名称不同但业务等价商品
- 同名不同规格商品
- 同名不同包装商品
- 品牌缺失商品
- 品牌冲突商品
- 系列或等级词商品
- 备注改变身份商品
- 名称中隐藏规格商品
- 规格列为空商品
- 多候选难区分商品
- 无法匹配商品

每类样本建议至少准备 3 到 5 条。

### 19.4 样本标注字段

每条样本至少应标注：

- 客户原始记录
- 我司候选
- 正确我司商品
- 人工判断理由
- 核心身份信号
- 强约束信号
- 弱约束信号
- 是否存在偏差风险
- 是否存在遗漏风险
- 应输出状态
- 是否允许自动落码
- 不允许自动落码的原因

### 19.5 标准答案确认

验证样本必须有人工确认的标准答案。

如果业务人员对某条样本也无法确认，应标记为争议样本，不应作为自动落码验收依据。

## 20. 验收标准

三期验收不以自动落码率为第一指标。

更重要的验收标准是：

- 不把核心品名冲突的商品自动落码
- 不把品牌冲突的商品自动落码
- 不把规格或包装冲突的商品强行自动落码
- 不忽略备注中会改变身份的信息
- 不擅自补充客户未表达的信息
- 能区分表达差异和商品身份差异
- 能给出业务人员看得懂的中文解释
- 人工审核人员能根据系统证据快速确认或修正
- 对“必须人工审核”和“未找到可靠匹配”不伪造确定编码
- 导出结果可直接用于业务审核

### 20.1 第一版最小验收

第一版至少应完成：

- 成功导入我司商品库
- 成功导入客户商品库
- 支持单条客户商品手工输入
- 支持字段含义确认
- 每条客户商品输出候选或未匹配说明
- 每条结果输出五档中文状态之一
- 每条结果输出中文推荐理由或风险说明
- 支持人工确认、修改、标记无匹配
- 成功导出编码对照表

### 20.2 验证样本验收口径

在第一批验证样本上，暂定验收口径如下：

- 自动落码中的严重错误应为 0。
- 严重错误包括核心品名错、品牌冲突、规格包装冲突、系统脑补客户未表达信息。
- “必须人工审核”和“未找到可靠匹配”不得伪装成已确认编码。
- 建议落码待确认必须清楚展示不确定原因。
- 候选结果应尽量包含人工标准答案；若未包含，应记录为候选漏召回问题。

上述指标是第一版默认口径。

后续可根据验证样本规模和业务风险调整。

## 21. 后续待讨论问题

以下问题不阻塞 v0.2 需求基线，但需要在后续业务流程、判断规则或技术方案中展开。

### 21.1 人工确认责任

需要明确：

- 谁有权确认编码对照结果
- 谁有权把人工确认沉淀为记忆
- 争议样本由谁最终拍板

### 21.2 商品库版本变化

需要明确：

- 我司商品库更新后，历史确认关系是否仍然有效
- 商品名称、规格、单位变化后，是否需要重新审核
- 记忆是否需要绑定商品库版本

### 21.3 结果撤销和修正

需要明确：

- 如果人工确认后发现错了，如何撤销
- 已导出的结果如何标记修正
- 错误案例如何进入失败记忆

### 21.4 业务商品身份判断表

需要整理：

- 哪些字段通常是核心身份信号
- 哪些字段通常是强约束
- 哪些字段通常只是弱信号
- 哪些词可以视为噪声

### 21.5 单位和包装等价范围

需要整理：

- 哪些场景下 `箱` 和 `件` 可以等价
- 哪些场景下 `瓶`、`罐`、`听` 可以等价
- 哪些包装差异必须人工审核

## 22. 后续文档顺序

本需求文档确认后，建议按以下顺序继续：

1. 三期 3.1 业务流程文档
2. 三期 3.1 低保真界面流程
3. 三期 3.2 判断规则文档
4. 三期 3.2 验证样本设计文档
5. 三期技术方案文档
6. 三期 1.0 执行计划

技术方案必须晚于产品定义和验证样本。

不要先让技术路线牵着产品走。

## 23. 总结

三期商品编码对照系统要先做到：

**看懂客户商品，找出我司候选，说清楚为什么，明确哪些能自动，哪些必须人工，并导出业务人员能使用的编码对照表。**

第一版的成功标准不是“自动匹配率高”。

第一版的成功标准是：

**能用，能看懂，不乱落码，结果能被人工审核。**
