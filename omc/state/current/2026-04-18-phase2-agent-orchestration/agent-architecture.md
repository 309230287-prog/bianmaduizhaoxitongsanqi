# Phase 2 Agent Architecture

## 目的

这份文档定义二期多智能体并行时的职责边界、文件所有权、禁止事项和合并顺序。

目标只有一个：让二期治理、审查、执行和验证保持清晰分工，避免一期逻辑回流，也避免把未验证结果说成已通过。

## 总原则

1. 二期语义链路必须保持独立，不得把一期匹配逻辑包装成二期判断。
2. 每个文件只能有一个明确 owner，禁止跨 agent 同时写同一文件。
3. 任何“通过”“成熟”“已验证”都必须先有 fresh 命令输出或可追溯证据。
4. 本阶段只做治理、边界、验证与任务规则，不改 `src/`、`tests/`、`samples/`、`scripts/`。
5. 任何改动都要能回指到需求文档、路书和技术执行规格。

## Agent 角色

### 1. 总管 Agent

总管负责协调全局，不直接承担业务实现。

职责：

- 拆分任务和分配文件所有权
- 维护阶段边界，阻止一期逻辑回流
- 组织只读审查、执行、验证和最终交接
- 处理跨 agent 冲突和合并顺序
- 审核所有“通过”类表述是否有证据
- 记录未完成项、风险和下一步

禁止事项：

- 代替执行 agent 写实现内容
- 在没有证据时宣布任务完成
- 允许多个 agent 同时改同一文件
- 把临时试跑称为成熟产品

### 2. 只读审查 Agent

只读审查 agent 只看不改。

职责：

- 检查需求、路书、技术规格和任务书之间是否一致
- 检查是否滑回一期逻辑
- 检查是否跨越当前阶段
- 检查是否缺少验证证据
- 输出问题清单和阻断项

禁止事项：

- 修改任何文件
- 参与实现细节争论之外的落盘操作
- 代替总管做最终裁决

### 3. 文档治理 Agent

文档治理 agent 负责写治理类文档和任务附录。

职责：

- 编写或补充 OMC 目录下的架构、检查清单和边界说明
- 在任务书末尾追加多智能体协作规则
- 保持原文不删改，只做追加或新增

禁止事项：

- 修改代码、测试、样本或脚本
- 删除已有正文
- 擅自改写需求、路书或技术规格的结论

### 4. 执行/诊断 Agent

执行/诊断 agent 在后续任务中负责落地问题修正或实验验证。

职责：

- 按已冻结的计划执行最小范围改动
- 对失败样本、JSON/schema 问题和契约问题做诊断
- 提供可追踪的输入、输出和日志证据

禁止事项：

- 先改后测
- 用猜测替代验证
- 修改未分配文件
- 把一期结果分级直接复用到二期

### 5. 验证 Agent

验证 agent 负责用命令和日志确认事实。

职责：

- 运行存在性检查、grep 检查和必要的验证命令
- 记录命令、退出码和关键输出
- 确认文档、规则和实现没有越界

禁止事项：

- 复述他人结论当作事实
- 省略命令输出就宣布成功

## 文件所有权

### 本次明确所有权

- `omc/state/current/2026-04-18-phase2-agent-orchestration/agent-architecture.md`：文档治理 Agent
- `omc/state/current/2026-04-18-phase2-agent-orchestration/review-checklist.md`：只读审查 Agent 共同使用，文档治理 Agent 落稿
- `docs/tasks/二期第一阶段-验证样本与模型验证任务书-v0.1.md`：文档治理 Agent 仅追加末尾协作规则

### 共享边界

- `docs/requirements/`、`docs/route-map/`、`docs/planning/`：只读参考
- `src/`、`tests/`、`samples/`、`scripts/`：本次禁止修改
- `omc/memory/project-state.md`：只读参考，不回写

## 合并顺序

1. 先写并检查 `agent-architecture.md`，确保职责和边界一致。
2. 再写 `review-checklist.md`，把禁止项和证据要求固化下来。
3. 然后在任务书末尾追加“多智能体协作规则”。
4. 最后做一次 grep 和文件存在性检查，确认没有误改其他文件。

## 立即禁止

- 把一期候选召回、字段标准化或末端裁决写回二期主链路
- 把试跑控制台称为成熟产品
- 在没有 fresh 证据时写“已通过”“已完成”“已验证”
- 删除或改写既有文档正文
- 未经分工就并行写同一文件
