# Phase 2 Review Checklist

## 用途

这份清单专门用于检查二期治理文档、任务规则和验证说明，重点防止四类错误：

- 滑回一期逻辑
- 跨越路书阶段
- 误称模型通过
- 缺少验证证据

## 检查方式

每一项都要同时看“文字是否正确”和“证据是否存在”。

如果任意一项失败，结论都应判为不通过。

## 1. 是否滑回一期逻辑

- [ ] 文档没有把一期字段标准化写成二期主路径
- [ ] 文档没有把“名称找相似”写成二期主要方法
- [ ] 文档没有把本地候选召回写成二期主判断入口
- [ ] 文档没有把“模型只在末端裁决”写成二期结构
- [ ] 文档没有把“自动落码率最高”写成二期首要目标
- [ ] 文档明确说明一期只可作为历史教训或少量工具性能力参考

阻断信号：

- 任何把一期匹配逻辑包装成二期语义判断的表述
- 任何暗示二期只是一期升级版的表述

## 2. 是否违反路书阶段

- [ ] 文档内容只落在当前阶段允许的范围内
- [ ] 没有把样本验证阶段直接写成完整产品化阶段
- [ ] 没有跳过“先验证，再产品化”的顺序
- [ ] 没有提前引入不在当前阶段的交付物
- [ ] 没有把候选池、原型或正式产品写成已完成事实

阻断信号：

- 直接宣称已经进入成熟产品阶段
- 在验证未完成时推进正式落码链路

## 3. 是否误称模型通过

- [ ] 所有“通过”“成功”“成熟”“可用”类表述都能指向具体样本或具体命令
- [ ] 如果提到模型验证通过，必须有 JSON/schema 验证结果
- [ ] 如果提到 10 条试跑通过，必须列出样本范围和结果记录
- [ ] 如果提到强自动落码可用，必须有错误样本排除证据
- [ ] 不存在把失败试跑改写成成功的描述

最低证据要求：

- 命令名
- 运行日期
- 样本范围
- 关键输出
- 退出码或成功判定依据

## 4. 是否缺少验证证据

- [ ] 文档里的结论能被命令输出、文件内容或日志支撑
- [ ] 重要结论没有只靠口头推断
- [ ] 如果说“已检查”，能找到检查命令和结果
- [ ] 如果说“已新增”，能找到对应文件路径
- [ ] 如果说“未通过”，能看到失败原因或失败记录

缺证据时的处理：

- 降级为“待验证”
- 不允许写成“已完成”

## 5. 允许接受的表述

- [ ] “当前仅完成试跑控制台骨架”
- [ ] “当前模型试跑未通过 JSON/schema 校验”
- [ ] “二期语义链路保持独立”
- [ ] “本次只做文档治理，不改代码”

## 6. 不允许接受的表述

- [ ] “模型已经验证成功”但没有 fresh 证据
- [ ] “二期已成熟”但仍在验证阶段
- [ ] “一期逻辑只是稍微复用”但实际复用了判断链路
- [ ] “已经通过”但没有命令输出、日志或样本记录

## 7. 审查结论模板

- 通过：所有检查项满足，证据齐全
- 有条件通过：文档无原则性错误，但存在待补证据项
- 不通过：出现一期逻辑回流、阶段越界、误称通过或缺证据
