## 1. 决策结论

三期 3.1 采用：

**Tauri + Web 前端 + Python 本地服务。**

产品形态采用：

**本地桌面工作台应用。**

用户体验目标：

- 像普通桌面软件一样双击打开
- 不需要用户手动打开命令行
- 不需要用户手动访问 `127.0.0.1`
- 不暴露 localhost、端口号、开发服务等技术概念
- 界面形态接近 Codex 这类桌面工作台
- 左侧导航，中间主工作区，右侧状态和证据面板

## 2. 为什么选择这个方向

### 2.1 用户体验更像正式软件

旧的浏览器 localhost 体验对业务人员不友好。

用户会看到：

- 浏览器地址栏
- `127.0.0.1`
- 端口号
- 启动脚本
- 命令行窗口

这会让产品像开发半成品。

三期 3.1 要改成桌面工作台：

- 用户双击图标打开
- 配置、导入、审核、导出都在一个窗口中完成
- 页面不再像临时网页

### 2.2 Web 前端适合做工作台界面

三期界面需要：

- 首页工作台
- 设置页
- 商品库导入页
- 字段确认页
- 候选和证据对齐页
- 人工审核页
- 导出确认页

这些界面用 Web 前端实现效率更高，也更容易做成现代工具型界面。

### 2.3 Python 适合本地数据和模型能力

本项目核心能力包括：

- Excel 读取
- Excel 导出
- 中文文本处理
- 商品候选生成
- 模型 API 调用
- 日志记录
- 本地数据存储

Python 在这些方面更合适。

特别是后续涉及大模型、文本处理、样本验证和数据分析时，Python 生态更顺手。

### 2.4 Tauri 更适合轻量桌面壳

Tauri 的价值是：

- 提供桌面应用外壳
- 内嵌 Web 前端
- 包体相对轻
- 更像正常桌面软件
- 可以和本地服务配合

第一版目标是轻量桌面工作台，不需要先上很重的桌面框架。

## 3. 和其他方案的比较

### 3.1 不采用纯 Web localhost 模式

不推荐：

```text
用户运行脚本 -> 打开浏览器 -> 访问 127.0.0.1
```

原因：

- 用户体验像开发工具
- 启动流程复杂
- 用户容易不知道系统是否真的启动成功
- 模型配置、文件导入、导出体验割裂

纯 Web 可以作为开发调试模式，但不作为正式产品体验。

### 3.2 不优先采用 Java

Java 可以做桌面软件，也可以做后端。

但三期 3.1 不建议用 Java。

原因：

- 桌面 UI 开发成本更高
- 现代工作台界面实现不如 Web 前端灵活
- Excel、模型 API、文本处理虽然能做，但整体开发效率不如 Python
- 当前阶段最重要的是快速跑通 3.1 主线，而不是建立重型企业级架构

Java 不作为三期 3.1 推荐技术路线。

### 3.3 Electron 作为备选，不作为首选

Electron 成熟，但相对更重。

如果后续 Tauri 在本机环境、打包、Python 服务协同上遇到不可接受的问题，可以考虑 Electron。

但三期 3.1 默认首选 Tauri。

### 3.4 PySide6 / Qt 作为备选，不作为首选

PySide6 可以做纯 Python 桌面应用。

但要做成 Codex 这种现代工作台体验，开发成本和设计弹性不如 Web 前端。

因此不作为首选。

## 4. 建议架构

三期 3.1 建议采用三层结构：

```text
Tauri 桌面壳
  -> Web 前端工作台
      -> Python 本地服务
          -> Excel / 候选生成 / 模型调用 / 导出 / 日志
```

### 4.1 Tauri 桌面壳

职责：

- 提供桌面窗口
- 启动 Web 前端
- 管理应用生命周期
- 后续负责打包和桌面入口
- 避免用户直接接触浏览器和 localhost

### 4.2 Web 前端工作台

职责：

- 首页工作台
- 初始化配置页
- 模型设置页
- 我司商品库导入页
- 客户商品库导入页
- 手工输入页
- 字段确认页
- 候选和证据展示页
- 人工审核页
- 导出确认页

前端应使用中文业务语言。

不应让用户理解：

- JSON
- 端口
- 向量
- 召回
- Prompt
- API 细节

### 4.3 Python 本地服务

职责：

- 读取 Excel
- 分析表头和样例
- 保存字段确认结果
- 生成候选
- 调用模型 API
- 整理证据对齐结果
- 保存人工确认记录
- 导出 Excel
- 记录日志和异常

第一版 Python 服务应只服务本机桌面应用。

不做公网服务。

不做 SaaS。

## 5. 3.1 技术边界

### 5.1 3.1 必须支持

- 双击打开桌面应用
- 首页显示配置状态
- 初始化配置入口
- 模型配置入口
- 我司商品库导入
- 客户商品库导入
- 手工输入
- 字段确认
- 候选结果展示
- 中文解释展示
- 人工审核
- 导出 Excel
- 基础日志
- 异常提示

### 5.2 3.1 不做

- 完整权限系统
- 多人协同
- 云端部署
- 复杂审批流
- 完整记忆管理后台
- 模型精调
- 多模型复杂编排
- 向量召回定型
- 大规模性能优化

## 6. 数据和安全原则

### 6.1 本地优先

三期 3.1 默认本地运行。

用户文件默认在本机处理。

### 6.2 API Key 不进代码

真实 API Key 不能写入：

- 源码
- 默认配置文件
- Git 仓库
- 原型文件

### 6.3 模型调用需要明确配置

如果启用模型能力，用户必须在设置中配置模型服务。

系统应显示：

- 当前模型是否启用
- 当前模型提供方
- 当前模型名称
- API Key 是否已配置
- 模型连接是否正常

### 6.4 不暴露技术细节给业务用户

业务用户不应该看到：

- localhost
- 端口号
- 后端服务启动日志
- JSON 原文
- Python 进程细节

这些只应出现在开发调试或日志文件中。
